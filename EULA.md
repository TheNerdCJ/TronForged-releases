### 11. The repair engine, Downloaded Tools and destructive operations

11.1 It changes things. The engine's cleaning, debloating, disinfecting, resetting, software removal, updates and restarts are changes, some irreversible, and its imaging, restore and data-recovery utilities can overwrite disks. It first checks that the system drive has room, may then delete the oldest restore points this computer holds (never one made during the current service) and limit the space Windows reserves for them when the drive is too full to make a new one, and then creates a restore point and checks that it exists. It keeps an undo record of the changes its own scripts make - each registry value, service start type, scheduled task, power plan and sleep setting, firewall rule set, hosts file and proxy setting it changes, saved just before the change in a folder only the computer's administrators can open - and a technician can revert a run's recorded changes from that record. The undo record does not cover files it deletes, apps it removes, the recent-file and search history and website notification permissions a cleanup clears (of which it keeps a copy only of the settings it changes, never of the history itself), or changes made by the Windows and third-party tools it runs, which only the restore point covers. It can resume after a restart, and gates the most dangerous operations (a whole-machine restore or a disk clone needs a dry-run plan and a typed confirmation, is limited to accounts the Shop has granted the restore permission, erases the destination disk, and refuses the running Windows disk as a destination - including when it cannot identify that disk, and a disk other than the one the technician picked; it restores or clones onto a disk that holds a selected external backup drive or an image library, or onto a disk it cannot measure, only after the technician types an override naming that disk and the Shop server records it, and no override reaches the running Windows disk; and an image whose fingerprints the Shop server has not signed is restored, cloned, started in a virtual machine or browsed only after a typed override that the Shop server records), but the decision to run them is yours. The Shop must hold the Customer's authority for the work, take its own backups, and bears the consequences.

11.2 Sensitive material. Optionally, before a repair the engine checks which of the computer's drives BitLocker protects and names them and their key protectors in the run's results, without copying any recovery key; it recovers product keys, which the Product Keys & Licenses report keeps where only the computer's administrators can open it, and, only on the technician's switch, exports saved Wi-Fi keys in plain text. A forensics collector, when a technician runs it, copies and hashes Windows artifacts - registry hives, browser databases, recycle-bin records and others - into a chain-of-custody bundle without modifying the computer, and on the technician's switch creates a shadow copy. The Software writes each bundle into a new folder that only the computer's administrators can open, on a drive that supports that; on a drive that cannot restrict access, such as most USB drives, or on a network share, it says so first, and anyone holding the drive or reaching the share can read the bundle. It proposes no folder on the computer's own system drive and asks before collecting there. After collecting, it sends the fingerprints of the bundle's two manifests and its report to the Shop server, which signs a record stating that it received those fingerprints from that computer at that time - the signature does not show how the evidence was collected - and only that record, never the evidence or the report, is attached to the chosen ticket as a file the Customer cannot see. The Software never deletes a bundle by itself; it offers to copy one out, checking every copied file, and only then to delete the original. A bundle collected before this version stays where it was, with the access it had there, until a technician locks or moves it. An image of a BitLocker-protected volume holds that volume's contents unencrypted (Section 13.1). Reports are filed on the computer. When a technician has chosen the ticket the work is for, the service report from a run attaches automatically to that ticket on the Shop server, where the Customer can see it, and the run's receipt, quality-control checklists, data-recovery reports (which name the disks, images and folders worked on) and technician-approved customer summaries attach to it as internal files the Customer cannot see. The Shop must treat all of this as confidential Customer material and use it only for the repair.

11.3 The engine restarts after updates and for Safe Mode disinfection; the console's self-repair loop never restarts on its own. The Software adds no antivirus exclusion for itself, and the Shop should not add one on a Customer's computer without the Customer's agreement.

11.4 Besides the Shop server, an installed console contacts tool vendors, Microsoft, the PowerShell Gallery, OEM updaters and GitHub for downloads - on the Shop's behalf, never the Licensor. A console sends no email.

11.5 What a service changes, and what it leaves alone.
(a) Firewall. A service never resets the Windows Firewall on its own. It removes only firewall rules that point at programs no longer on the computer, after saving the full rule set to the undo record, and re-creates the Software's own rule if it is missing. A full firewall reset is a manual repair a technician chooses; it saves the rule set first and re-creates the Software's own rule, but rules other programs had added are lost until those programs add them again.
(b) Proxy. A service resets the computer's proxy settings only when its malware checks found them hijacked, and records the previous settings in the undo record. A proxy set by the Customer's organisation is otherwise left in place.
(c) Debloat. A service removes only the apps on the removal list that came pre-installed with Windows or by the computer's maker; it never removes a copy the Customer installed, and it keeps Media Player, Films and TV, Get Help, the Microsoft 365 app and Clipchamp. It also switches off Windows' own suggested-app and promotional content for each user of the computer, so removed apps are not reinstalled by Windows, and it blocks device makers' companion apps from installing automatically when a device is plugged in.
(d) Power. A service keeps the computer awake while it works, saves the power plan and sleep and display settings it found, and puts them back when it ends, including when it is stopped early. It changes the power plan only when the technician chooses one.
(e) History. A cleanup may clear recent-file lists, jump lists (keeping pinned items) and address and search history, and may reset website notification permissions that were allowed, naming each site in the report; it saves a copy of the notification settings and jump lists it changes, for the undo record, before clearing them.
(f) Optional privacy and update settings. Only when the technician chooses them: Windows diagnostic data set to the minimum Windows allows, advertising and activity-history settings switched off; Copilot, Recall and similar Windows AI features switched off by Windows policy (the features are not removed); and Windows Update set to Microsoft's defaults or to a security-only preset that delays feature updates. A preset that stops Windows updating is never offered. Each is recorded in the undo record.
(g) Restore points. Deleting old restore points (11.1) is reported, including how many were deleted and how much space was freed; restore points deleted cannot be recovered.
(h) Defender Offline. A technician may start a Microsoft Defender Offline scan, which restarts the computer and scans it before Windows loads; the computer is unavailable until it finishes.
(i) Advanced Tune-Up. Only when the technician chooses the Advanced Tune-Up service or one of its settings: further Windows privacy and performance settings are changed for each user of the computer and for new users - feedback prompts, advertising and tips, Bing results in Start search, typing and inking data collection, background game recording, the startup-app delay and Fast Startup switched off, Windows' data-collection scheduled tasks disabled, and two rarely used services set to start only when needed. Settings a Customer would notice (Windows' telemetry services, error reporting, location services - which Find My Device uses -, visual effects, Edge running in the background, Widgets, background apps and OneDrive sync) are changed only one at a time, after a warning. OneDrive is never uninstalled, and its sync is not switched off while a user's Desktop, Documents or Pictures are kept in it. None of these changes Microsoft Defender, SmartScreen, User Account Control, Windows Update, the firewall, BitLocker or Windows' other security protections, and each is recorded in the undo record.

11.6 Data destruction (Secure Data Erasure). The Secure Data Erasure feature permanently overwrites the drives you select. Erased data cannot be recovered by the Software, by us, or by anyone else, and no backup is taken first. You are solely responsible for choosing the correct drive, for having the authority of the drive's owner to destroy its contents, and for any copy you need before erasing. The Software refuses the drive Windows is running from, boot, system and recovery drives, the drive it is installed on, and drives it knows hold backups or image libraries; these safeguards reduce risk but do not remove it. Overwriting a solid-state drive cannot reach the drive's spare or remapped blocks, and such a drive may still hold recoverable data; the certificate says so. A firmware erase is performed by the drive itself; the Software reports it as complete only when the drive confirms completion. A certificate of erasure records what the Software wrote and, where the method defines it, what it read back; it is not a guarantee that no data can be recovered by laboratory means, and it does not by itself certify compliance with any law, regulation or standard. ### 12. The Shop server: the only place the data lives

12.1 The Shop server's database holds the Shop's users, console credentials, Customer records, tickets, invoices, the backup catalog, diagnostics, chat presence and an IP-stamped audit log; Authorised persons (names, telephone numbers, email addresses, what each may do, whether each is sent updates, and any sign-in of their own); for each Customer, the address its ticket updates go to, or that it asked for none; per ticket, who collected the device, whether they were on the Customer's list and whether staff ticked that they checked photo ID (the ID itself is never recorded) (a correction is kept as a new record; an earlier record is never changed); each Customer or Authorised person sign-in (a username that is their email address, a salted and peppered password hash, hashes of its recent passwords and of the passwords the Shop sent it - kept so an old one cannot be reused - who created it and when, and whether, and by whom, it was allowed to see the Customer's backups); a record of each email the Shop server sends a Customer or an Authorised person (the address, the kind of email, when, and whether the mail server accepted it - never its text and never a password); and the queue of ticket updates waiting to be sent; technicians and Authorised persons are data subjects of it too. The Shop server also keeps its own operational log - connections, refused connections and sign-ins, and errors, each with the address it came from and any user name involved - for ninety days, and then deletes each day's file; technicians and Customers are data subjects of that log too.

12.2 What every console reports, with no opt-out. Each enrolled console sends the Shop server a regular beat (machine name and label, a hashed installation identifier, Windows version, whether the computer is a physical PC or a virtual machine and, if virtual, the hypervisor's name, uptime, online and alert state, CPU load and free memory, whether the display is on or asleep, the main screen's size, whether a repair run is in progress, what it is doing (a service run, a maintenance run, a backup or restore and whether it goes to the Shop server or a local drive, with the time it expects to take) and whether it has proved it is on the Shop's own network - for which it connects every few minutes to the Shop server's local-network address, and may therefore try that address on whatever network it is on (these are held in the Shop server's memory and not stored), and how long its last check-in took to reach the Shop server (these are held in the Shop server's memory and not stored), and about daily its missing Windows updates and pending restart) and redacted diagnostic records (run outcome, stage results, a crash fingerprint and a scrubbed message - never a stack trace - in which paths, share names, email addresses, network addresses, host names (the computer's own name included) and card-number-shaped digits are replaced; a short run-log tail travels only when a run failed; and, from release 0.449.9, a record each time the .NET 10 Desktop Runtime, PowerShell 7 or the PawnIO sensor driver fails to install or verify, or a start is refused because one is missing: the component, the step, the reason and exit code, whether Windows was in Safe Mode, the Windows build and processor type, where the installer came from, and the last lines of the Software's own prerequisites log (at most 200 lines or 16 KB, scrubbed the same way); a computer not yet connected to the Shop server keeps these records and sends them once it is connected). These records also include, with personal data, user names, computer names and file paths removed or masked before they leave the computer: each repair step that failed, timed out or was skipped and why; each Windows Fix's result with the Windows build and error; moments when the program's window stopped responding for several seconds and what it was doing; errors the program handled internally; crashes and failed updates of the program and its helper service; Windows' own application-error records for the Software's programs; and, from release 0.455.0, how each transfer of data from one computer to another (Data Migration) ended on each of the two computers - whether it finished or stopped, where it stopped and the message it showed, how many items and how much data it moved, how long it took, how often it reconnected after a dropped connection, whether it went over Wi-Fi, and how many programs were reinstalled or left for a technician (counts and sizes only, never the names of files, programs or users). The Shop server adds its own errors. They go only to the Shop server, which groups them and lets the Shop export them to help fix the Software; nothing goes to the Licensor unless the Shop sends it. The server keeps daily medians for four hundred days and raw run and tool records for ninety; full crash detail leaves a computer only by a manual Support Bundle. The Shop server also stores, for each console, the version of the Software it last reported and when it last reported it. Only disconnecting or uninstalling stops it.

12.3 Encrypted at rest, from release 0.453.0: the Shop server's database is encrypted as a whole (SQLCipher, AES-256) under a key derived from the Shop server's own secret, which is kept sealed to the server computer and which the database files, the daily database snapshots and backup files do not contain; the daily database snapshots and any manual database backup file are encrypted under the same key, except that a manual backup made with a recovery key is encrypted under that recovery key instead, which is shown once and stored nowhere. A database from before release 0.453.0 is encrypted at the Shop server's first start on that release, and its unencrypted copy is kept beside it for seven days and then deleted; a Shop server that still keeps its data in PostgreSQL (set up before release 0.368 and not moved) is not encrypted by the Software. Password hashes are also salted and peppered, and from release 0.449.4 a sign-in password for a Customer's device that the Shop records with a ticket is sealed with a key derived from the Shop server's own secret. This protects the files, not the running server: anyone with administrator rights on the server computer can read the Shop server's own secret, and whoever has that secret and the database files, a snapshot or a backup file - or a backup file and its recovery key, or the unencrypted copy while it exists - can read everything in them and impersonate any console. Disk encryption, physical security, the server computer's accounts, recovery keys and those snapshots and backup files are the Shop's responsibility.

12.4 The Shop server must be reachable on a public address with one forwarded port; Customers never forward anything. Exposing it to the internet is the Shop's decision and risk, and the Shop must keep the server updated.

12.5 The Software deletes no Customer data on its own, except that the Shop server's operational log (Section 12.1) deletes each day's file after ninety days, the Shop server keeps only its newest seven daily database snapshots (Section 12.3) and deletes older ones, and it deletes the diagnostics of Section 12.2 once the periods stated there pass; and a disk image a technician sends to the Shop server alone is first written to temporary space on the computer, which the Software deletes once the Shop server confirms that the copy it stored matches - if the upload fails, the temporary copy is kept so it can be sent again; and a disk image a technician captures to, or downloads into, an external backup drive is first written there as ordinary files, which the Software deletes once the encrypted copy it makes from them has been read back and, when the image is also sent to the Shop server, once that upload has ended. The Shop server's crash log records the server's own errors, which can name whatever an error touched, and is started afresh once it passes 512 KB. Stored backups and images can be deleted by hand from the Shop server (Section 13.3); a device sign-in password recorded with a ticket (Section 16.6) stays until someone at the Shop removes it or the ticket is deleted; everything else the Shop must meet its own retention and deletion duties for, by other means where the Software offers none. A person taken off a Customer's account stays named in the pickup records and messages that already name them; deleting a sign-in deletes its password history; erasing a Customer's records at the Shop's request also removes its Authorised persons and any ticket updates still waiting to be sent; and a ticket update still waiting after 12 hours is dropped, and the ticket says so.

12.6 The Shop's app cache. When a console on the Shop server's own network installs or updates an application through winget, or downloads an operating system image (ISO), the Shop server keeps a copy of that installer or image in its own folder (never with the backups) and serves it to the Shop's other consoles on that network instead of the internet. Only the newest version of each is kept. A console uses a cached copy only when it is exactly the file it would have downloaded itself: an installer must match the hash the Windows Package Manager publishes for that computer, and an image must be the release its publisher serves at that moment and, where the publisher lists hashes, match them. Consoles outside the Shop server's network are never served. Each cached file remains under its publisher's terms (Section 5); the Shop is responsible for whether its licences allow keeping and reusing such copies.

### 13. Backups in the Shop's custody

13.1 Backups are sealed by the Shop server when they arrive, not by the computer before they leave. The console sends the content over its encrypted connection to the Shop server, and the server encrypts each piece under a per-backup key before writing it to its store, so the stored files are ciphertext but the server handles the content in the clear on arrival and holds the key. From release 0.449.6, a file or registry backup, or a disk image, that the Software copies to an external backup drive the Shop selected is encrypted with a key the Shop server holds: opening it needs a technician whose account holds the restore permission, on a console connected to the Shop server, or the Shop's recovery key file together with the passphrase chosen when it was saved, and the Licensor cannot recover that key or that passphrase. To encrypt a disk image the Software first writes it, and to use an encrypted one it first opens it, as ordinary files on that drive, and it deletes those files by overwriting their beginning and then deleting them; on flash or solid-state storage parts of them may remain recoverable. Copies made before release 0.449.6 stay unencrypted until a technician chooses to encrypt them, and Windows system images, which Windows itself writes, are not encrypted by the Software. Anything else the Software copies to a destination the Shop chose - a folder on a local disk or an SMB share - is written as ordinary files with no encryption of its own. On a local drive that supports it, the Software restricts each disk-image folder it creates, and a new or empty image library folder, to the computer's administrators; an existing image library is left as it is unless a technician chooses to lock it, and on an SMB share or a drive that cannot restrict access the Software warns and changes nothing there. New images are no longer stored under the Program Files folder by default; images already there stay where they are. That includes the contents of a BitLocker-protected volume, which the image holds in the clear; a volume restored or cloned from an image is not encrypted until the Shop or the Customer turns BitLocker on again.

13.2 The Shop can read them by default: per-backup keys are wrapped under the server's own secret, so the Shop can restore and read a Customer's backup without the Customer present, and must protect that data and use it only for the Customer's purposes. There is no customer-held passphrase: that option, which no console ever offered, and its escrow were removed in release 0.449.6, so treat every backup as readable by the Shop. From that release a disk image is downloaded from the Shop server only by a technician whose account holds the restore permission; a Customer's own sign-in, and each person on a business Customer's account, can download that Customer's file backups but not its disk images. The Licensor cannot recover any key in any case.

13.3 Deletion is manual, not automatic. Choosing Shop server alone for a disk image is a choice to keep it only on the Shop server: its temporary copy on the computer is deleted once the Shop server confirms its copy. Choosing External drive or Both for a disk image is a choice to keep it encrypted on that drive: the ordinary files written first are deleted once the encrypted copy has been read back, and, for Both, once the upload to the Shop server has ended. When the Shop moves the Shop server's backup location, the Shop server copies everything stored at the earlier location to the new one, checks each copy by reading it back, and then stops reading from the earlier location; it never deletes anything there - the Shop deletes those files itself when it chooses. A technician can delete a stored backup or image from the Shop server, and a Customer can ask the Shop to do so; there is no automatic deletion, the store otherwise only grows, and per-Customer quotas are enforced at upload. Nothing deletes a Customer's data without somebody choosing to. Disk images older than 90 days are flagged for review, never deleted automatically, and uninstalling the Software keeps any disk-image folders stored in its program folder.

13.4 Restores and clones run from inside Windows only, onto a second disk; a clone captures the running computer and restores that image onto the chosen disk in one job. "Boot in VM" runs an image under Hyper-V for inspection only; Windows may report itself unactivated there, and it is not a way to run a Customer's Windows license. The Shop must test the backups it relies on.

13.5 Data Migration. Data Migration copies, from the old PC to the new PC chosen by the technician: the folders ticked (Desktop, Documents, Downloads, Pictures, Music, Videos, Favorites, Contacts); the user's application settings and data (the AppData folder: Roaming, Local and LocalLow), except caches, temporary files, crash dumps and folders Windows keeps per PC; the settings ticked (Wi-Fi networks with their passwords, network printers, browser bookmarks, wallpaper, mapped drives, taskbar pins, the screen saver); and, for programs marked Average, their program folder and the user's registry settings for them; for programs marked Good, the user's own registry settings for that program. Programs marked Good are reinstalled from the winget source. Data Migration does not copy Windows Credential Manager, the Windows Vault, Windows data-protection keys, certificate private keys or Windows Hello, and saved passwords that applications protect with the old PC's Windows account (including Chrome, Edge and other Chromium browsers, Outlook and Microsoft 365 sign-ins) will not open on the new PC; the customer must sign in again. Files held open by a running program may be skipped; they are listed in the migration summary. Both PCs are normally enrolled to the same shop server, which issues a one-time key for the transfer; when the technician connects the two PCs directly by local network address, the two PCs agree the key between themselves and the shop server is not involved. Either way a technician confirms a matching code on both screens before anything is sent. The shop server records each pairing and transfer in the shop's audit log; the files themselves travel directly between the two PCs over the local network, encrypted, and are not stored on the shop server. For the transfer, the receiving PC opens a temporary Windows Firewall rule limited to the local network, which is removed when the transfer ends or after 10 minutes. Before receiving, the receiving PC creates a Windows restore point. Some programs cannot be moved and must be installed again from their own installers; TronForged reinstalls supported programs with the Windows Package Manager (winget), subject to each program's own licence terms, which remain the customer's responsibility. A migration package saved to a USB drive is encrypted with the shop's key; anyone holding the shop's key or recovery file can open it.

13.6 Moving from the old PC's drive. When the old PC cannot start, a technician may connect its drive to the new PC, and Data Migration then copies the chosen user's files, application data, browser bookmarks, wallpaper, taskbar pins and the screen saver from that drive into a user of the new PC. The old drive is only read; nothing is written to it. Wi-Fi passwords cannot be moved this way. A drive protected by BitLocker must first be unlocked by the technician with its recovery key, which the Software does not ask for or keep. Before copying, the new PC creates a Windows restore point; this route does not use the shop server or the local network.

13.7 Programs and the receiving user. From the old PC's drive, Data Migration also reads that computer's registry files (from copies; they are never loaded into the new PC's registry), lists its programs, and installs the ones the technician ticks on the new PC through the Windows Package Manager (winget), each under its publisher's terms (Section 5), before putting back that program's settings and the user's application data. When the new PC has no user of the old user's name, the technician may create a local Windows account for the Customer on the new PC; with no password typed, the Customer chooses one at the first sign-in. The account's creation and each move from a drive are recorded in the Shop server's audit log.

### 15. Optional AI features

15.1 AI features are opt-in and default off. Each feature also has its own switch. Turning AI on switches on the three features that existed before release 0.426.0 (the fleet health summary, the draft customer summary and the server-sizing snapshot of Section 15.2); every feature added since, starting with the ticket brief, stays off until the Shop switches it on by itself. A Shop that turns them on supplies an Anthropic API key or a Claude Code sign-in on the Shop server; consoles never call a model. All AI traffic leaves from the Shop server, to Anthropic, under the Shop's own account and Anthropic's terms; the Licensor is not in the chain.

15.2 What is sent, feature by feature, each only while its own switch is on: a fleet health summary from the redacted diagnostics of Section 12.2; a draft customer summary from the recorded results of one repair run, without the Customer's name, the ticket number or where the report is kept (used only if a technician approves it); a numeric server-sizing snapshot; from release 0.426.0, a brief of ONE support ticket for the technician working it, which carries that ticket's subject, the Customer's own messages on it (including those of anyone the Customer has given their own sign-in), and the Shop's replies and internal notes on it; and, from release 0.428.0, a draft of a reply or a resolution for ONE support ticket, which carries that ticket's subject and only the messages the Customer can already see on it - never the Shop's internal notes - and, for a resolution, the summary of work the Software composed from the Shop's work records. A draft is returned to a person at the Shop, who edits and sends it; when a message began as such a draft, the Software adds a line at its end telling the Customer it was written with the help of an AI assistant. The Software cannot label text a person types or pastes in from elsewhere. Text shaped like a password, key, recovery code, network address, host name or payment card number is masked before a ticket brief is sent; that is a check on the SHAPE of the text, not a guarantee that no secret is sent. Calls are audited by token count and by ticket number, never by message content, and each signed-in person is capped at a fixed number of AI requests a day. The optional training export is an explicit administrator action; the training pipeline itself is not in any release and never runs on a Customer's computer.

15.3 A model never acts on a machine: no tools are declared, the command-line route runs with tools disabled, and model output is never parsed or dispatched, only shown, labelled AI-generated. A draft reaches a Customer only when a person at the Shop sends it. The Shop is responsible for what it sends to its provider, including any personal data in it, and for the provider's terms and cost.

15.4 AI features and regulated customers. Ticket features that use AI run only when the Shop connects them to Anthropic's API; they never run with a subscription sign-in. For a customer the Shop marks as healthcare, legal, financial or government, AI is off unless an administrator records that the Shop has a business associate agreement or zero-data-retention agreement covering that use; the record names who made it and when, and changing how the Shop connects to the AI provider cancels it. Fleet-health and server-sizing summaries contain no customer messages and are not affected.

### 16. Payments, accounting, email and the Shop's other services

16.1 Square. Card payments run through Square under the Shop's own account, and a card is entered, and saved for later use, only on Square's own hardware or hosted pages. From release 0.447.0 the Software records a card payment by the card's brand and last four digits only; it refuses text shaped like a full card number where staff and customers type text into it (a customer's request for support from their own computer keeps its message, with the number masked instead); and it masks such text in what the Shop's server sends to Square and to the AI provider, in invoices, accounting exports and invoice email, and in its audit log and diagnostics. That is a check on the SHAPE of the text, as in Section 15.2, not a guarantee. Team chat is encrypted by the consoles, so the Shop's server cannot check it; a console refuses a card number before sending one. A number typed before release 0.447.0 stays stored, and in the backups and exports made since, until the Shop removes it as the server guide describes. The Shop's obligations under Square's terms and card-network rules are its own.

16.1A What the Shop server sends to Square. While the Shop has switched Square on, and only for the features it has switched on, the Shop server - never a console - sends Square: for a payment link, a Terminal charge or a deposit, the amount and the invoice or ticket number; for an invoice the Shop sends through Square, each line's description and amount, the tax as Square sales tax on each taxed line, the due date and the Customer's name, company, email address and telephone number, and Square, or the Shop if it chooses to share the link itself, delivers it; for a refund, the Square payment it reverses, the amount and the reason the Shop typed; for a product the Shop sells through Square, its name, SKU, price and stock count. When a person at the Shop asks, the Shop server reads the items in the Shop's Square catalog (their names, SKUs and prices) to link them to the Shop's items or add them to the Shop's stock list with no stock. A Customer's record at Square is created only when the Shop first sends that Customer an invoice, saves a card or starts a plan, and carries the name, company, email address, telephone number and the Software's internal reference - never an address, a note, a device or a ticket's contents. An estimate the Shop gives a Customer is never sent to Square; once the Customer or the Shop approves it, it becomes an invoice and is handled as one.

16.1B Saved cards and plans. A card is saved at Square only after the Customer has agreed to it in words the Shop chooses; the Software records that agreement (its wording, when, how and which staff member took it) and refuses to save a card without one. The Software keeps only the card's brand, last four digits and expiry month and year as Square reports them. A Customer may withdraw that agreement at any time and the Shop must then remove the card, which the Software does at Square. A plan the Customer agrees to is billed by Square on its schedule, and each charge is recorded in the Shop's books.

16.1C What the Shop server reads from Square. The Shop server asks Square regularly about payments, refunds, invoices, plans, disputes, payouts and stock sold outside the Software; Square does not connect to the Shop server. Once a day it also compares Square's payments and refunds with the Shop's records, changing neither, and lists any difference for a person at the Shop. It also reads the items on the Shop's Square counter sales to check that Square charged the Shop's sales-tax rate, keeping only the order and the amounts. A sale Square records reduces the Shop's stock in the Software, and the Software's stock is the master; a count changed in Square's own dashboard is shown to the Shop and is not overwritten until a person at the Shop keeps the Shop's count or takes Square's. A dispute is shown to the Shop; no money moves because of it.

16.1D Refunds and deposits. A refund the Shop makes through the Software is sent to Square, limited to what was paid and, above an amount the Shop sets, to a second staff member's approval; the Shop's books change only when Square confirms it. A deposit may be set at the cost of the parts on the job, so labour can be paid later, and is held as a credit for the Customer until the Shop applies it to an invoice or refunds it.

16.1E Deposits into the Shop's bank. The Software keeps Square's records of the deposits Square made to the Shop's bank account, with each charge, refund and fee, so the Shop can see them and export them for its bookkeeping.

16.1F Without Square. Invoicing, payments, refunds, deposits and stock work in full without Square; switching Square off stops every new message to Square, and the Software finishes settling only what was already open at Square while the Shop's Square token stays stored.

16.2 QuickBooks. Export writes Intuit's QuickBooks Desktop (.iif) and QuickBooks Online (.csv) formats; no Intuit software or API is used and nothing syncs. From release 0.449.12 it also writes QuickBooks Online journal entries, including sales tax, which a person imports into QuickBooks Online, and a sales-tax summary for a period; these are prepared from the Shop's own records, what Square reported and sales tax worked out under Section 16.8, and are a starting point for the Shop's bookkeeping, not tax or accounting advice. The Shop is responsible for its books, its tax returns and its taxes.

16.3 Email. Invoices - to the email address on the Customer's record and, as separate copies, to each Authorised person the Shop has set to receive updates, even when the Customer has no email address of its own; sign-in details, when a sign-in is created for a Customer or an Authorised person or the Shop sends new ones - the one-time password in that email is made by the Shop server, held only in its memory until the email is sent, and never stored or logged, and it works only until the person chooses their own; only after the Shop switches it on, ticket updates carrying the text of the Shop's replies on a ticket and its note when the ticket is finished (never anything the Customer or an Authorised person wrote), sent to the address the Customer chose for them (or to none, if it asked for none) and to those Authorised persons, gathered per Customer and never sent more than 12 hours late; a notice of each finished repair run sent to the people the Shop lists, appointment reminders to the Customer, a copy of a form the Customer signed, when the Shop sends one, and a purchase order the Shop approves, sent to the supplier's address the Shop recorded, listing the items, quantities, prices and the Shop's own details - never Customer details - go out from the Shop's own SMTP mailbox through the Shop server; a console sends no email and keeps no mail password. A run notice carries the technician, the ticket number, the computer's name, counts and the outcome - never a report or a file; a notice the computer could not hand to the Shop server yet waits on the computer for up to seven days and is then dropped. Messages carry no tracking. An appointment reminder carries the Shop's name and telephone number, the kind of visit, its date and time, the ticket number, the technicians' names and, for a visit to the Customer, the address; a signed-form email carries that form as one PDF file, with a short note naming the form, the date, the ticket number and the Shop's name and telephone number.

16.4 The Shop server contacts Anthropic, Square (including, when the Shop switches it on, what the Shop server reads from Square under Section 16.1C), Cloudflare (dynamic DNS), S3-compatible storage, Amazon Business, the Shop's SMTP provider, a web address the Shop names for run notices, the address services of Section 16.5 and the sales-tax sources of Section 16.8 (the Streamlined Sales Tax Governing Board's rate and boundary files, the TaxLocus dataset, the Census Bureau geocoder's geographies service and the Washington Department of Revenue's rate lookup) only when the Shop configures them; GitHub, for releases, about every six hours unless the Shop pauses the update pipeline (Section 6.3), anonymously unless the Shop has stored a GitHub token; and, whenever the Shop advertises a public address for its server, Cloudflare's public address-echo service to learn that address. The Shop server reaches the address services and the run-notice web address only over HTTPS, and it refuses to send to any of them, or to the Shop's mail server, at an address on the Shop's own private network unless the Shop switches that on in the server's settings file, and always at the Shop server's own address. When the Shop connects AI through a Claude Code sign-in, the Shop server runs Anthropic's command-line program for each request in a temporary folder of its own that is deleted afterwards, with the program's telemetry and error reporting switched off. All of these run under the Shop's own contracts; the Licensor is not party to any of them.

16.5 Address lookup. Address lookup is off until the Shop switches it on in the Server Console, and each service has its own switch. While it is on, the Shop server - never a console - sends the address text a person at the Shop types into an address box, and nothing else about the Customer (no name, email address or telephone number), to the services the Shop has switched on: for suggestions, the Photon service operated by komoot, or another Photon server the Shop names; and, to check an address a person has chosen, the geocoder of the United States Census Bureau, or another geocoder the Shop names. Each request carries the Software's name and version and, when the Shop has entered them, the Shop's contact email and, for suggestions, the Shop's location. Each service also sees the Shop server's public IP address and the time of each request. Suggestions are OpenStreetMap data, available under the Open Database License, and are credited to OpenStreetMap contributors wherever they are shown; a person at the Shop chooses a suggestion or ignores it, and nothing is saved until that person saves the customer. A Census check says only whether the house number falls within an address range the Census Bureau knows; it does not confirm that mail can be delivered there. Answers are kept in the Shop server's memory to avoid repeating a request and are gone when it restarts; the audit log records that a lookup was made, never the address. The Shop is responsible for sending its Customers' addresses to these services and for their terms.

16.6 Booking in, device passwords, signed forms and reminders. When the Shop books a device in, the Shop server keeps what the Customer left with it, who dropped it off, the job type, the technicians assigned and any appointment. At collection, the Shop server records who collected the device (by name when it was not the Customer), whether their photo ID was checked, and which items were returned. A sign-in password the Customer gives for the device is stored sealed (Section 12.3) with that ticket for as long as the ticket exists, can be shown only to a technician assigned to that ticket, records each showing in the audit log with the technician's name and the time, and is never placed in reports, emails, the ticket's messages, what the Customer sees, the Software's AI features or its logs; the Shop removes it when it no longer needs it. Forms the Customer signs - on screen, on a signature pad or on paper - are kept exactly as signed with their date, version and the staff member who took them, and a PDF copy is attached to the ticket. The form texts the Software ships are examples only: the Licensor gives no legal advice, the Shop chooses and is responsible for the terms it asks Customers to sign, and should have its own lawyer review them. Appointment reminders go to the technicians assigned and, unless the Shop switches them off for that appointment, to the Customer by email and as a notice on a computer of the Customer's that runs the Customer console and is linked to that ticket. When the Shop books a device in, or at any time from the Customer's record or a ticket, it may print labels for the Customer, the device and each item brought in, showing the Customer's name and telephone number, the Shop's own details and a barcode. The barcode holds only an internal reference; scanning it opens the Customer's record only for the Shop's signed-in staff with permission to see it.

16.7 Amazon Business ordering. Off unless the Shop switches it on and enters its own Amazon Business credentials, which are sealed on the Shop server. When on, a purchase order the Shop has approved is placed with Amazon once, carrying the items, quantities and the Shop's delivery details - never Customer details - under the Shop's own Amazon account and terms.


16.8 Sales tax. The United States has no federal sales tax; sales tax is set by states and local governments, and the Shop must register, collect, file and pay in each place the law requires. The Software works out sales tax from the rates, jurisdictions, taxability answers and exemption certificates the Shop's server holds, freezes the result on each invoice when it is sent, and reports it by jurisdiction.
