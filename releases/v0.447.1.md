# v0.447.1 - Security release: card numbers, locked data folders, tighter offline sign-in

This release follows v0.446.0, and these notes cover everything that changed since then. It includes everything in v0.447.0, which was never offered as the latest release: v0.447.0 was checked before release and replaced by this version, which fixes what that check found. v0.447.0 is published for the record only, and shop servers, consoles and new installs go straight from v0.446.0 (or older) to v0.447.1. If your shop server has not taken v0.446.0 yet, read the v0.446.0 release notes too: everything in them applies to this update as well.

This is a security release. In short:

- **Keeping card numbers out of TronForged.** A card payment records the card's brand and last four digits, text shaped like a full card number is refused where people type, and invoices, exports and what the shop server sends to Square, the AI provider and diagnostics mask one. The shop server also looks for card numbers typed before this release, says on its Status page what it found - including when it found none - and can remove them.
- **Recording a refund and voiding an invoice need a new permission, refunds.** Until you grant it, only administrators with full access hold it.
- **Each PC's TronForged data folder is locked** to that PC's administrators and Windows itself. Reports and logs open inside the console, and the two commands that opened the data and config folders in File Explorer are gone.
- **Offline sign-in is tighter.** It lasts 72 hours on the shop's own PCs, is never kept on a customer's PC, and is erased when your shop server disconnects the PC. Each technician needs one online sign-in on each laptop after the update.
- **A repair run leaves less behind on the customer's PC.** It no longer copies BitLocker recovery keys, takes a picture of the desktop only when you ask, and saves only the registry keys it changes.
- **Update day is smoother.** With your shop server on this release, a PC set up for unattended access offers itself again within about a minute when its code is replaced on the day it updates, and a payment recorded just as the server restarts for its update is answered as recorded when it is sent again.
- **Reports print better from the console's viewer**: its **Print** asks the web engine to leave out its page header and footer, and the health bar and gauges now print.

This release updates the consoles and the shop server's program. For a shop server already on v0.442.0 or later, it does not change the structure of your shop's database. The licence changes too - see **The licence** below.

### Before you let your shop server take this update

- **If your shop server is older than v0.446.0** (the Server Console's **Status > Server program** shows its version), do the steps under *Before you let your shop server take this update* in the v0.446.0 release notes first. Above all: check which logins are linked to a customer, and on a server older than v0.442.0 make a copy of the database before it updates - updating from there adds to your shop's database, and no older server opens it afterwards.
- **Plan to update the shop server first, by hand** (see **After you update**), before your other PCs take this release. Unattended access on the day a PC updates, the card-number rules, the refunds permission and the new offline sign-in all work best, or only, with the shop server already on this release.
- **Plan for offline sign-in.** When a technician laptop takes this update it drops every offline sign-in it holds. Each account gets one back only when it signs in on that laptop online while both the laptop and the shop server run this release. A laptop that updates before the shop server keeps no offline sign-in at all until the server has updated. So once both have updated, have each technician sign in once at the shop on each laptop they use, after the laptop shows the new version and before it goes off-site. A laptop can finish an update when it next starts, which may be somewhere with no shop server to sign in to.
- **If a console emails run notifications through a mail account** (a user name set in the `config\notifications.json` file in TronForged's data folder) with SSL/TLS turned off, turn it on now: `"useSsl": true`, with `"port": 587`. TronForged's mail uses STARTTLS, which mail providers usually offer on port 587; port 465 does not work. From this release a console never sends a mail password over a connection without TLS, so those notifications stop until it is on. Edit the file from an editor run as administrator.

### After you update

- **Update the shop server by hand as soon as you can:** on the server PC, **Server Console > Settings > Updates for this PC > Update everything on this PC**. The card-number rules, the refunds permission, the new offline sign-in and unattended access on update day all depend on the shop server running this release.
- **Bring the Server Console on the server PC to this release too.** Updating the shop server does not always update the console on the same PC straight away: new console versions reach your PCs through **Console updates**, canaries first. On the server PC, open **Server Console > Settings > Console updates**. Under **Which consoles get updates first (canaries)**, set the server PC's own console to **Canary (first)** - or release this version to everyone from the catalog - then press **Update everything on this PC** and, when it appears, **Restart now to finish**. You need this console on this release to grant the refunds permission from it and to see the new Status lines.
- **Look at the Server Console's Status page.** Each time it starts, the shop server looks through its own database for text shaped like a full card number, and the Status page says what it found, under its health line:
  - "Card-number check (*time*): no card numbers found in this server's database" means it checked and found none;
  - "Checking this server's database for stored card numbers..." means the check is still running. Look again later;
  - a **red** line - "*n* value(s) shaped like a full card number are stored in this server's database" - means it found some. Nothing was changed. See **A card number typed before this release** below;
  - a **plain** line about the audit log means some sit inside the audit log. The audit log is tamper-evident and is never rewritten, so they stay;
  - an **amber** line means the server could not check - for example because it still runs on PostgreSQL. The check and the removal work only on the embedded database: move the server from **Set up server > Database engine** first, and it checks at its next start;
  - "This shop server did not report a card-number check" means the shop server is older than v0.447.0: update it;
  - no card line at all means the page could not ask the server.

  These lines need the Server Console itself on this release. On an older Server Console, open **Audit log** and find the newest **carddata.scan** entry: `none` means nothing was found, and an entry such as `table.column=n` names where numbers were found. The red, plain and amber lines refer to a server guide and a checking script that are not part of this download; this section and the next say what to do, and you can contact us for either.
- **Grant the refunds permission** to everyone who records refunds or voids invoices: on the server PC, **Server Console > Users & groups**, press **Edit** on their group, tick **refunds** and press **Save**. Existing groups are not given it when the server updates. The **Accountant** preset includes it, but applying a preset replaces all of a group's ticks, so tick the box instead if the group has others you want to keep. No technician or Reception preset includes it. Grant it from a console on v0.447.0 or later - in practice, this release: a console older than that does not show the box, and saving a group from one removes **refunds** again. From this release, a group editor keeps every permission it does not show. Changing a group's permissions - a grant included - also ends its members' offline sign-ins at their laptops' next contact, so have them sign in online once afterwards.
- **Sign in online once on each technician laptop**, at the shop, as above. The sign-in window says so when a laptop has no offline sign-in saved, and, from this release, when a saved one has expired.
- **On a PC that BitLocker protects, record the customer's recovery key before you start a run.** TronForged no longer copies it (see **Repair runs**), and the run's warning does not stop the run.
- **If you filed any of the shop's own PCs under a customer** in **Customers & fleet** (for example under a customer record for your own shop), those PCs no longer show tray alerts for customer requests, whoever is signed in.
- **If anything on your PCs reads TronForged's data folder from an ordinary account** - a shortcut to a report or log, a backup job, a script of your own - it can no longer read it. Open reports and logs from the console, or run the job as administrator.

### Card numbers

- **Take payment records a card's brand and its last 4 digits.** For a card, the dialog offers **Card brand** (Visa, Mastercard, American Express, Discover or Other card) and **Last 4 digits**, and the payment is recorded as, for example, `VISA ****4242`. There is no box a whole card number fits in. A cheque or transfer reference is at most 64 characters.
- **The shop server refuses a card number in a hand-recorded payment**, a card payment whose reference holds more than 4 digits in a row, a payment method other than cash, card, check or transfer, and a hand-recorded payment that claims to come from Square - only the server records Square's payments, when Square reports them.
- **Text shaped like a full card number is refused where staff type it** - tickets, replies and internal notes, work records, customer, site and asset records, invoices, time entries, user and group names, and the server's settings - and where a customer types it, in their shop account and in their support thread with the shop. Staff are told to record only the card's last 4 digits; a customer is asked to remove the number and send the message again. A customer's **Request support from a technician** note is the one exception: it still reaches you, with the number masked, so the request for help is never lost.
- **Reports that become ticket files refuse one too.** **Save QC Report** refuses when the technician name or the checklist's notes hold a card number; **Approve and insert** refuses an AI customer summary whose approved text holds one; and the Data Recovery report is not saved when anything in it - an image file name typed in the save box, for example - holds one. Each says why.
- **A card number typed into the Customer name box** on the **Automated Service** tab (used when no ticket is being worked) is cleared from the box the next time it is used - when a run starts, for example - the status line says why, and that job is filed as a walk-in with no name. The job itself goes ahead.
- **Team chat on a console that runs this release refuses a card number before sending.** Chat messages are encrypted by the consoles, so the shop server cannot check them.
- **No check reads the files attached to tickets.** Do not attach a file that holds a card number.
- **The check is on the shape of the text**, not a guarantee: 13 to 19 digits that could be a card number, in the ways people write one. It also refuses some long serial and tracking numbers - about 1 in 100 numbers of 13 to 19 digits, and about 1 in 40 of those exactly 16 digits long. If a number that is not a card number is refused, leave it out of that text.
- **Invoices and what leaves for other services mask text shaped like a full card number**, including one typed into a customer record, a ticket's device or an invoice before this release: invoices on screen, printed and emailed, QuickBooks exports, the software diagnostics the consoles report, and what goes to Square and to the AI provider. A number appears as `[card number ****1234 removed]`. The audit log masks one in every new entry. A console that runs this release also masks one on an invoice it prints. Like the refusal, this is a check on the shape of the text, not a guarantee: a number typed before this release is safest removed. Tickets, customer, site and asset records and the other screens inside TronForged still show a number typed before this release until it is removed (see **A card number typed before this release**).
- **The note TronForged attaches to a Square pay link is now "Invoice #N"**, the invoice's number, instead of the invoice memo, so the memo no longer goes to Square.
- **If Square reports a payment that is already recorded against a different invoice**, TronForged no longer marks this invoice's charge as done: it leaves it for you to check in the Square dashboard and record by hand.
- The Tech, Ticket and Customer boxes of the Remote tab's REMOTE CONTROL panel refuse a card number too.

### A card number typed before this release

A number typed before this release stays stored until it is removed. The Status page tells you whether the shop server's database holds one (see **After you update**), and the server program can remove it from the embedded database (a server still on PostgreSQL must move first - see **After you update**):

1. On the server PC, open the Server Console and press **Stop service** on its **Status** page.
2. Open PowerShell or Command Prompt as administrator, in the folder that holds `TronForged.Server.exe` (`C:\ProgramData\TronForged\server` on a standard install), and run `.\TronForged.Server.exe --redact-card-numbers` (type the `.\` - PowerShell does not run a program from the current folder without it). If your server keeps its data in another folder, add `--data` and that folder. This changes no stored value; it records the listing in the audit log. It lists every value it would change - the table, column and row, and the card's last four digits and brand, never more. It then names each daily database snapshot it will **replace** (one that holds a number, or that it could not read or fully check) and each it **keeps**, lists apart the numbers in the audit log, which it leaves as they are, and names the copies it does not change. It ends by telling you the count and the code to confirm with.
3. Read the list. **A snapshot it replaces becomes a copy of the cleaned database, so the day that snapshot was taken is gone from it.** If you may need one of those days, first copy the server's `backups\db` folder (`C:\ProgramData\TronForged\server\backups\db` on a standard install) somewhere safe, and keep that copy as carefully as the snapshots - it holds the numbers. Then run the same command again with `--confirm`, the count and the code it printed. It refuses if anything changed since the listing. It replaces each number with its last four digits, writes one entry in the audit log, compacts the database so the old text is gone from the file, and replaces the snapshots it named; every other snapshot is kept as it was. If it says to run the listing again, do so.
4. Press **Start service** on the Status page. At its start the server looks again, and the red line clears.
5. The command changes only the live database and the snapshots it names. Any other copy of the database - a set-aside copy, a backup export (`.tfbak`), a copy on another drive or a NAS - still holds the number: delete it, or replace it with a fresh backup made after the removal. If you have the checking script, run it again afterwards: **GREEN** means no stored number is left in what it reads.

What the removal does not reach: copies of the database you made yourself or keep elsewhere (step 5), PostgreSQL exports, QuickBooks exports already made, invoices already emailed or printed, payment notes already sent to Square, text already sent to the AI provider, team chat messages, files attached to tickets (service, QC and recovery reports and approved customer summaries are stored sealed on the server, where no check reads them), and each console's own copies of its reports. Nor does it reach the PostgreSQL database that a server which moved to the embedded database keeps for **Roll back to PostgreSQL**: it still holds any number typed before the move, and while it is there the checking script cannot read **GREEN**. **Set up server > Database engine > Retire PostgreSQL...** deletes it, once the server runs on the embedded database - after that there is no going back to PostgreSQL. A read-only script for checking backup files and exports exists; it is not part of this download - contact us if you need it.

A card number found stored may be a card-data incident for your shop under your card processor's rules and your state's law. Decide who at your shop handles it.

### Refunds and voids

- **Recording a refund and voiding an invoice need the refunds permission** (see **After you update**). Administrators with full access hold it already. Without it, a console that runs this release does not offer **Record a refund** or **Void & reissue**, and says that a correction needs the refunds permission; the shop server refuses both whichever console asks.
- **A refund of a card payment taken through Square is made in Square's dashboard first, then recorded in TronForged.** On an invoice Square was paid on, **Record a refund** asks which money is going back under **Paid by**: one of the invoice's Square payments, with what is left to refund of it, or *Cash, cheque or transfer*. Choosing a Square payment fills in what is left of it. One Square payment can be refunded in several parts, never past what it took.
- A console older than this release cannot name a Square payment, so on an invoice Square was paid on, it can refund only the cash, cheque and transfer money until it updates.
- **While your shop server is still older than v0.447.0**, a console on this release offers **Record a refund** and **Void & reissue** to whoever that server allows - such a server has no refunds permission - until the server updates.
- **A payment or refund recorded just as the shop server restarts for its update** is answered as recorded when it is sent again from the same window, instead of being refused by this release's new checks. This needs the shop server on this release.

### The data folder, reports and logs

- **The data folder is readable only by the PC's administrators and Windows itself.** It holds the PC's connection details, customer reports, run logs and job history. Three folders stay readable to the PC's other accounts: the downloaded tools, the downloaded Windows installation files, and the console's own program files - so a taskbar pin made from the running console still opens it. TronForged locks the folder when it installs, every time it starts, and every hour while its background service runs, and takes back access anyone else was given - including what File Explorer's **Continue** button granted before.
- **To edit a file in the config folder by hand**, open it from an editor run as administrator.
- **If a domain policy stops the lock**, the technician console's **Settings** tab says so beside where TronForged is installed, the PC's diagnostics tell your shop server, and TronForged starts anyway.
- **Reports and logs open inside the console.** **Open Report** after a run, the reports the **Reports** tab builds (including the **Product Keys & Licenses** report), the QC, recovery, triage and network reports, and the run logs open in the console's own viewer. A report has **Print**, **Page setup...** and **Copy to...**; a log has **Copy to...** and shows its last 4 MB when it is longer. A copy is only as private as the place you put it.
- **Open Reports Folder** and **Open Logs Folder** (and the tray's **Open reports folder** and **Open logs folder**) list the files inside the console. A new support bundle is shown in the console's list of support bundles: use **Copy to...** to take it where it needs to go.
- **The tray's Open data folder and the Settings tab's Open Config Folder are gone.** Opening the locked folder in File Explorer would offer to give your Windows account access to it. **Open Tools Folder** still opens File Explorer.
- **A run's report no longer opens by itself in a web browser**, including a run that resumes after a restart. After a run the console watched, press **Open Report**; for a run that resumed after a restart, open its report from the ticket's **Files > On this PC**, or find it with **Open Reports Folder**. A failed run's log still opens by itself, now in the viewer.

### Printing a report

This applies to reports printed with the viewer's **Print** - the service report, the device reports (Battery Health, Storage Health, System Summary, Installed Programs) and the other reports the console builds:

- **The viewer's Print now tells the web engine to leave out its page header and footer** (the page address, the date and the page numbers).
- **The service report's health bar and the device reports' gauges now print**, and the labels in the reports the console builds (such as *SMART OK*, or a failure warning) print as outlined coloured text.
- **The Print / Save as PDF button inside the reports the console builds is gone** - the device reports, the QC checklist and the recovery, triage and network reports among them: print them with the viewer's **Print**, like every report. A report saved before this version still shows that button, and printing with it adds the header and footer - use the viewer's **Print** instead.
- **To print the rest of a report's colours** - such as the coloured banner behind the shop's logo or name - press **Page setup...** and tick **Print background colors and images**.
- **For a PDF**, choose the **Microsoft Print to PDF** printer where Windows has it, or use **Copy to...** and open the copy in a browser.

### Installing and updating

- **Installing over a PC where TronForged is running can fail** with a message that the file is being used by another process, as in earlier versions. When it does, nothing on the PC has been changed. A PC that already has TronForged takes its updates from your shop server.
- **Each start of TronForged now checks the installed program's permissions**, and gives it back its folder's permissions if an earlier update or a rollback left it openable only by administrators, so its shortcuts start it and show its icon again.
- **A technician console, or the Server Console, no longer restarts by itself into a downloaded update while the shop server is out of reach.** **Install now** still installs an update when you choose it. An update already downloaded still finishes the next time TronForged starts, wherever the PC is, and the step into this release runs in the older version's code - so after an update, sign in once at the shop before a laptop goes off-site, as above.
- **Once the shop server answers again, a waiting update installs by itself as before** - also on a console that was signed in offline.

### Offline sign-in, and technicians on a customer's PC

- **On the shop's own PCs** (technician consoles and the Server Console), offline sign-in now lasts **72 hours** from that account's last online sign-in on that PC. It was 14 days. Staying signed in does not extend it: sign out and in again at the shop before leaving for off-site work. It grants only what the shop server signed for that account on that PC. Ten wrong offline passwords in a row still wipe the PC's offline sign-ins.
- **When the 72 hours have run out, the sign-in window says that account's offline sign-in expired, and when.** When the shop server cannot be reached, it still names the reason first. Sign in once while the shop server can be reached.
- **When the shop changes an account** - resets its password, changes its permissions or those of a group it is in (a grant included, such as **refunds**), disables or deletes it - that account's offline sign-in on a laptop ends the next time anyone signs in on that laptop while the shop server can be reached, or within about a minute while the laptop is signed in and connected. A laptop that does neither before it leaves the shop keeps it until its 72 hours run out. A password the shop server refuses also removes that account's own offline sign-in on that PC; a sign-in refused because the account is locked out does not.
- **A PC your shop server refuses** (disconnected or revoked) erases all its offline sign-ins when it hears the refusal: at sign-in, when the sign-in window opens, or, while it is signed in, once the server has refused it a few times in a row as it reconnects. Enrolling it again is the way back. A server that cannot be reached, or one that is not your shop's, erases nothing.
- **A customer's PC keeps no offline sign-in.** A technician who signs in there with **Technician sign-in...** leaves no offline sign-in behind, and one an older version left there is removed at the customer console's next start, together with anything else an interrupted visit left. The visit still lasts at most two hours, and it cannot be extended; the shop server now ends it at two hours too on a PC it lists as a customer's (**Customers & fleet > Role...**). A PC enrolled before console roles existed shows as Unclassified there: set its role, so the server's two-hour limit applies to it too. A technician who needs to work offline on site uses their own laptop.
- **A computer filed under a customer in Customers & fleet shows no tray alerts for customer requests**, even with a technician signed in there, once the shop server runs this release.

### Unattended access

- **Each armed PC's unattended-access code is replaced once**, the first time this release starts there, as a precaution. There is nothing to do.
- **With the shop server on this release**, a PC whose code is replaced while an older copy of TronForged on it is still waiting for a technician is asked to offer itself again, within about a minute. TronForged on this release also notices a new code by itself while it waits. With an older shop server, if an unattended connection to a PC is refused on the day it updates, restart TronForged on that PC - restart the PC, or have its user sign out and back in. That is why the shop server should update first.
- **If a PC cannot replace its code**, TronForged removes the old one, and unattended access stays off on that PC until it is turned on again there.
- **Where a PC's own policy stops TronForged making the code private** (some company PCs), unattended access does not arm, a connection to that PC is refused with a reason, and the PC's diagnostics tell your shop server why.

### Email from a console

- **A console never sends a mail password over a connection without TLS** (see **Before you let your shop server take this update**). The TLS is STARTTLS, usually on port 587; port 465 does not work. A mail relay that needs no user name still works as before.
- **The mail password is sealed to each PC.** A password typed into `config\notifications.json` is moved into a sealed file on that PC the next time the console starts, and the field is emptied. To change it, type the new one into the file (from an editor run as administrator); it is sealed at the next start.
- **If a console goes back to a version older than v0.447.0** - its own rollback after a failed update, or a reinstall of an older build - it finds the field empty and sends no mail: type the password into `notifications.json` again.

### Repair runs

- **No BitLocker recovery key is copied to the PC any more.** Before anything risky, the Prep stage checks which drives BitLocker protects. The run's results and its service report name those drives and tell the customer to keep the recovery key somewhere other than that computer, in words written for the customer. The run's log keeps the technician's instruction: each drive's recovery-key protector, and how to read the key - run `manage-bde -protectors -get C:` from an administrator prompt and store the 48-digit key somewhere other than that PC, or confirm it is saved in the customer's Microsoft account, Entra ID or Active Directory. The run does not wait, so do it before you press **Start Service**. Prep now ends with a Warning on every PC BitLocker protects: that is the reminder, not a fault. The Scheduled Maintenance profile does not run this check.
- **Key files earlier versions saved stay where they are**, readable only by that PC's administrators. TronForged does not delete them while it is installed, because one may be the customer's only copy. **Uninstalling TronForged removes the whole data folder, those files with it**: copy them somewhere safe first if one may be the customer's only copy. **Uninstall / remove completely** on the technician console's **Settings** tab, and **Force uninstall...** on a customer console, say how many such files they are about to delete, when there are any; uninstalling from Windows' list of installed apps, or with **Force-uninstall TronForged from this PC** in the downloaded TronForged.exe, does not ask.
- **A run saves each registry key its own scripts are about to change, just before the change**, in that run's own folder, readable only by the PC's administrators - except the recent-file and search history a privacy clean erases on purpose. It never exports a whole registry hive any more. Changes made by the Windows tools and scanners a run starts - power settings, network and firewall resets and the like - are covered only by the restore point made at the start of the run, when Windows allows one (the run's results say whether it was made).
- **The Restore tab's Registry backup** (**Open Folder**) lists the saved keys inside the console. A whole-registry *HKLM.reg* or *HKCU.reg* that an older version left there is kept, locked: select it and choose **Remove** when you no longer want it. TronForged never removes one by itself.
- **A picture of the desktop is taken only when you ask.** Tick **Take a picture of the desktop for this ticket** on the **Automated Service** tab before you press **Start Service**; the box clears itself at each start. It is never taken on an unattended run, a single stage run on its own, or a run started from a remote session, and it is saved where only the PC's administrators can open it. Before, most service profiles took one on every run. Pictures earlier versions took stay where they are, readable only by the PC's administrators.

### Drafts and disk images

- **An unsent reply draft shows how old it is** under the reply box, and **Discard draft** removes it after asking. A draft more than a week old asks whether to discard it. Nothing deletes a draft on its own.
- **A customer's own login can no longer upload a disk image**, fresh or resumed: *Only the shop can upload a disk image.* Customers' own file backups are unchanged.

### The licence

The licence now describes this release. Clause 5.2 says what TronForged checks about a tool it downloads; 9.5 the 72-hour offline sign-in and when it is erased; 10.7 that nothing that would let a technician sign in offline is written to a customer's computer; 11.1 and 11.2 what a repair run saves (the changed registry keys, no BitLocker recovery key, the private Product Keys & Licenses report); 12.2 and 15.2 that card-number-shaped digits are masked in diagnostics and before a ticket brief is sent; 16.1 how card payments and card numbers are handled; and 19.3 the locked data folder, the program files other accounts on the computer can still read, that an old BitLocker key copy stays while TronForged is installed and is removed with the data folder when it is uninstalled, and the desktop picture taken only when asked.

### While the consoles and the shop server are on different versions

Your consoles update from your shop server, and the server updates its own program when the shop is quiet, so for a while some may be ahead of others.

- **Decided by the shop server, whatever the consoles run:** refusing card numbers where people type (an older console shows the server's own message), the checks on a recorded payment, the masks on what the server sends, masking a card number in a customer's support request, the refunds permission, no tray alerts on a computer filed under a customer, the two-hour limit on a technician's session on a PC the server lists as a customer's, refusing a disk image from a customer's login, asking a PC to offer itself again when its unattended-access code changed while an older TronForged on it waited, and answering a payment retried across the server's update restart as recorded. They take effect when the server updates.
- **Need the console and the shop server both on this release:** offline sign-in on the shop's own PCs (see **Before you let your shop server take this update**), ending a changed account's offline sign-in at the next contact, naming a Square payment when you record its refund, and the card-number lines on the Status page - which also need the Server Console itself on this release (see **After you update**). A console older than this release keeps its old offline sign-ins, as before, until it updates.
- **Work on each console as soon as it updates, with any shop server:** the locked data folder, the in-console viewer and its printing, the repair-run changes, the mail rules, reply drafts, the unattended-access code, the card brand and last 4 digits in **Take payment**, the chat check, the card-number checks on the QC checklist, an approved summary, the Data Recovery report and the **Customer name** box, the message for an expired offline sign-in, the group editors keeping every permission they do not show, and the installed program's permissions. With a shop server older than v0.447.0, a console on this release offers **Record a refund** and **Void & reissue** as that server allows, until the server updates and you grant the refunds permission.
- **A console older than v0.447.0 does not know the refunds permission:** saving a group from it removes **refunds** from that group. Edit groups from a console that runs this release.
- **On a customer's own PC**, the customer sees reports open inside the console and finds no picture of their desktop taken unless the technician asked for one; once the shop server runs this release, they are also asked not to send a card number in a message to the shop.

### Known issues

- **None of this release has been tried on real shop hardware yet.** It was tested on the build machine, with the server's own code and its real database engine, not on a shop server or customer PCs. In particular, the first lock of a PC with months of reports, the viewer on Windows 10 and 11 and what its **Print** puts on paper, the one-time replacement of the unattended-access code and a PC offering itself again after it, the 72-hour offline sign-in and its erasing, a taskbar pin, and the installed program getting its permissions back have not yet been seen on real PCs.
- **Some of this release's own checks need administrator rights** - among them the ones that prove each lock reads back closed - and were not run with them on the machine this release was built on.
- **The shop server's card-number check reads only its embedded database, and the removal only that database and its daily snapshots** - neither works on a server still on PostgreSQL (see **A card number typed before this release**).
- **Some long numbers that are not card numbers are refused** too - a device serial among them (see **Card numbers**).
- **A console older than v0.447.0 can still remove the refunds permission** from a group it saves (see **After you update**).
- **Any change to an account's permissions ends its offline sign-ins**, even a grant such as **refunds**: have the account sign in online once afterwards.
- **The viewer cannot show a picture or a PDF**, such as the desktop picture or a run's PDF: use **Copy to...** and open the copy.
- **The Restore tab cannot import a saved registry key yet**, and File Explorer no longer opens that folder. Try the restore point first; if you need one key back, select it in **Registry backup** (**Open Folder**), use **Copy to...**, and import the copy from an administrator prompt with `reg import`.
- **Installing over a PC where TronForged is running still fails**, as in earlier versions (see **Installing and updating**).
- **A technician's visit on a customer's PC does not survive a dropped connection or a shop server restart.** The session cannot be extended, so the technician has to sign in again.
- **A technician laptop whose console never recorded its role** (one set up long ago and never reinstalled) says at sign-in that it is a customer's computer and keeps no offline sign-in. An administrator signed in on it can press **Change role** in **Settings** and choose the technician console; it takes effect the next time TronForged starts.
- **The viewer uses the web engine built into Windows**, so a report can look plainer than in a browser. If one does not display properly, use **Copy to...** and open the copy.
- **For a run that resumed after a restart, Open Report can stay unavailable** even when the console picks the run up: open the report from the ticket's **Files > On this PC**.
- **The Automated Service tab's stage list still describes Prep as taking a desktop snapshot and a registry backup.** It takes a picture only when the box is ticked, and saves only the keys it changes.
- **The BitLocker line names only drives that have a recovery key.** On a PC where one drive has a recovery key and another is encrypted without one, the second is not named: check with `manage-bde -status`.
- **A repair run resets the PC's sleep and display timeouts.** It turns them off while it works and sets fixed values at the end (on mains power: display off after 15 minutes; sleep after 30 minutes on a PC with a battery, never on a desktop), not the ones the customer had. This is not new in this release; check them after a run.
- Further security work is under way and will follow in the next releases.
- Still open from earlier releases:
  - **Servers set up from the Server Console before v0.446.0 keep an unlimited default backup quota** until you set one (v0.446.0 notes).
  - **Tray alerts, and team chat through the shop server, stop without saying so once a console's sign-in runs out**, 12 hours after signing in or somewhat later. Right-click the TronForged icon in the notification area, choose **Close TronForged**, then open TronForged and sign in again. Very rarely, a customer's request or reply arrives without an alert; it is still in the Service Desk.
  - **Automatic restarts do not wait for everything yet**: not for a maintenance run, the part of a Safe Mode scan or Windows-updates run that resumes after its restart, or a customer's own backup on a customer console. If the countdown appears while one runs, press **Not now (1 hour)**.
  - **If you have not yet linked every customer's login to its customer** on **Users & groups**, do it now, as the v0.446.0 notes describe.
  - **Install helper can report a replacement with the same version number.** This is harmless.
  - **A reinstalled PC can be asked about its own tickets** (*Run here anyway?*). Choose Yes, or use **Change machine...** on the ticket.
  - **Files > On this PC can list an old report under a ticket that only shares its number.** Check the customer and the date of an older report before you use it.
  - **On Users & groups, a refused change can give the wrong reason**; **Edit** shows the server's own reason. While the not-saved warning shows, the Square and Email pages still say a token or password "is saved on the server".
  - **If consoles cannot reach the shop server after it updates from a version older than v0.442.0**, open the Server Console on the server PC and press **Settings > Updates for this PC > Update everything on this PC**. Your data is intact.
  - **Leave address lookup switched off for now**; untick **Mail goes to this address** before **Packages ship to this address**; and after **Edit contact details**, open the customer again from the list before editing a second time (v0.439.0 - v0.441.0).
