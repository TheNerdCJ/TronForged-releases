# v0.418.0 - the build tests the real server against a real database

## v0.418.0 - the build now tests the server against a real database

**No change to anything you can see.** This release is about what the build checks before a
release reaches you, and it closes a gap that had been open since the server moved to its
embedded database.

### The two halves that were never tested together

The build had two ways of testing the shop server, and neither was the real thing:

- One drives the real server code end to end - but against a stand-in store held in
  memory, which cannot enforce a rule, refuse a bad write, or undo a half-finished one.
- The other drives the real database - but with none of the server code near it, so no
  actual operation is ever performed against it.

So "the server saves this correctly" was being proven against something that cannot say
no, and "the database is right" was being proven without the code that writes to it.
Anything that only goes wrong where the two meet was checked by nothing at all.

There is now a third check that runs the **real server against a real database file** on
every build: writes go to disk, the database's own rules apply, and the file is closed and
reopened to confirm what was saved is really there.

**It found something the first time it ran.** The test data was written the way all the
existing in-memory tests are written - and the real database rejected it, because it
refers to a technician who does not exist and the real schema does not allow that. The
in-memory stand-in had been accepting records the shipped database will not take. That is
exactly the class of problem this was built to find, and it found one immediately.

### A build check that was watching the wrong folder

The build has a check whose only job is to catch one specific mistake: a test project that
is missing a source file it needs, which makes it fail to compile.

Last release made exactly that mistake, and the check said nothing - it was only looking
at one of the two folders where shared code lives, and the new file was in the other. It
was watching the wrong place for the same mistake it was built to catch.

It now covers both. Verified the way this project requires: the mistake was deliberately
recreated, the check was watched failing and naming the missing file exactly, and then the
code was put back.

### Worth knowing

**Nothing in this release changes the product's behaviour** - no screen, no setting and no
stored data is different. It changes what has to be true before a release can be built.
