# TronForged v0.488.0

Manage the shop server from any technician console without remoting into it, and safer, broader Windows Server management.

## Run the Server Console from any technician console - no remote session into the server

You no longer have to remote into the Windows server to manage it. On a technician console signed in with
an account that has the "server.manage" permission, press **Server administration**:

- **No second password.** The Server Console uses your sign-in on that console. It then asks for the
  6-digit code from your authenticator app, and the shop server will not let another computer change
  anything without it - even if two-factor sign-in for staff is turned off. One code lasts while you
  work; after 15 minutes without use it asks again. If your account has no authenticator app yet, the
  Server Console offers to set one up right there. Every code given and every refusal is in the audit log.
- **A Status page of its own**, read from the server itself: its version, how long it has been running,
  its port, the database, failed sign-ins and lockouts in the last 24 hours, releases, backups and PCs
  that have gone quiet.
- **Restart the server** from the Status page. Windows brings the service back a few seconds later. If a
  remote session, a transfer or a Windows-update install is running, you are told and asked to confirm.
- **Read the server's log** (the last 200 lines, with passwords, keys and card numbers masked).
- **Take a database snapshot now** and see the snapshots (Settings > Database maintenance). Restoring a
  database is still done on the server itself.
- **See and empty the shop app cache** (Settings > Shop app cache).
- **Update the server now** (Settings > Console updates).

## The server updates itself, with nobody signed in on it

Set up server now adds a scheduled task, "TronForged Server Update", that runs every 15 minutes as SYSTEM. With
automatic updates on, the server looks for a new server program every six hours. When nothing is in flight it
downloads it and checks the owner's release signature and its SHA-256. The task then checks both again, swaps the
program, restarts the service and waits for it - and puts the previous program back if the new one does not start.
Every step is in the audit log. A server installed before this release gets the task the next time you run Set up
server > Update server on it; until then the Server Console on the server updates it as before.

Installing, updating in place, reinstalling and uninstalling the server, and restoring its database, stay
on the server itself. The Server Console on the server is unchanged and never asks for the code.

## Fixed

- The server's count of failed sign-ins and lockouts could read 0 on a busy shop: it looked only at the
  newest 500 audit entries, which a few thousand PCs reporting Windows updates fill in minutes. It now
  counts every entry of the last 24 hours.

## Windows Server management: safer by default, and more you can do

**Who may do what.** Everyday changes on a customer's Windows Server still need the Windows Server management permission. A new
**Windows Server - read only** permission (winsrv.read) shows the Windows Server tab and its lists and changes nothing - not even
a password reset; the Junior tech preset now holds it instead of Windows Server management. Two more permissions sit on top:

- **Windows Server admin** (winsrv.admin) is needed for anything that cannot be undone: deleting a user, group, computer or
  virtual machine, turning a VM off, applying or deleting a checkpoint, offboarding a user, turning a Group Policy link on or
  off, removing a node or destroying a cluster.
- **Windows Server privileged** (winsrv.privileged) is needed to change a domain administrator or any other protected account or
  group (Administrator, Domain Admins, the built-in admin and operator groups, a domain controller's own account).

**Action needed after updating:** nobody receives these automatically. An administrator grants Windows Server admin, in Settings >
Manage users, to the people who should be able to delete and turn off on customers' servers. The Senior tech preset includes
it; Junior tech does not (it is read-only now). Only Owner (all) includes Windows Server privileged. Every account that held
Windows Server management before still holds it and can still make every everyday change; an administrator who wants a group
read-only unticks Windows Server management and ticks Windows Server - read only.

**New on a domain controller**

- For a user: Change details (display name, email, job title, phone, manager), Move to another OU, Show groups (and remove the
  user from any of them), Add to a group, Account expiry, Password never expires, and Offboard - disable the account, reset its
  password to a random one nobody is told, remove it from every group and move it to an OU, with one confirmation and every step
  reported.
- New user can copy a template user's groups, department, office, title and OU, and now sets the user's sign-in name
  (user@yourdomain) and first and last name.
- The user list can show only locked, disabled or stale accounts.
- A new Group Policy section lists every Group Policy object and where it is linked, backs them all up to a folder on the server,
  and turns a link off or on.

**New for virtual machines:** Save, Pause, Resume, Turn off, and checkpoints (show, apply, delete). The list shows each VM's CPU
use, checkpoints, disk size, whether it is clustered and its replication health. On a cluster, a role that is not a virtual
machine (a file server, for example) can be moved to another node, started or stopped, and the running cluster can be checked
without taking its disks offline.

**Safer**

- A virtual machine is identified by its id, so a renamed VM, or a cluster role with a different name from its VM, is never
  mistaken for another. Restart is always the guest's own restart, never a hard reset.
- A virtual machine is deleted only when it is off. Deleting its disks keeps any disk another VM uses, shared VHD Sets and disks
  outside the cluster's shared volumes, says which were kept and why, and is refused while the VM has checkpoints.
- A new user is created disabled, given its password and only then enabled; if any step fails the half-made account is removed.
  "Already exists" now says whether it was the sign-in name or the full name.
- A password reset that cannot also unlock the account, or set "must change at next sign-in", says so instead of failing.
- Objects protected from accidental deletion are not deleted; deleting a user also removes its child objects.
- Group members show each member's type and include members whose primary group it is.
- Pausing a node is refused when no other node is up, and says afterwards what is still on it. A cluster that still has any role
  cannot be destroyed.
- Only one technician at a time can change a cluster; the other is told who is busy with it.
- Servers named in a cluster action must be enrolled consoles of the same customer, and are recorded in the audit log.
- An authorisation can be used once even across a restart of the server's helper or of the shop server.

**Faster and clearer:** Active Directory lists are searched on the domain controller a page at a time, so large directories stay
quick. While a long action runs the page shows what it is doing; a second click says another action is still running. If a remote
session drops during an action, the page waits for it to come back and then shows the result. Reading a list is no longer
written to the audit log; every change still is.

These new actions need the TronForged helper 0.488.0 or later on the managed server (it updates with the console). A server
whose helper has not updated yet shows the previous buttons, and the shop server is stricter with it until it does.
