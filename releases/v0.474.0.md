# v0.474.0 - TronForged 0.474.0 - a combined update: safer backups and restores, steadier updates, PostgreSQL removed

## TronForged 0.474.0 - a combined update: safer backups and restores, steadier updates, PostgreSQL removed

This is one combined update. It carries everything built since 0.463.0: the planned releases 0.464.0 to 0.473.0 were
never published on their own, and all of their changes ship here together. It also removes the old PostgreSQL database
support from the shop server.

### Before you update: PostgreSQL is no longer supported

Shop servers have used the built-in database since release 0.368. The code that ran a server on PostgreSQL, and the
tool that moved a server off it, are now gone.

If your shop server still keeps its data in PostgreSQL (set up before 0.368 and never moved), this release will not
start it. The server stops with a message telling you to move it first with TronForged v0.463.0 or older. Do the move
with that version, then update. Asking the server to migrate a PostgreSQL setup stops with the same clear message, and
the restore error no longer tells you to roll back to PostgreSQL.

### Backups on the shop server

- A nearly full backup location is protected for every kind of file. Ticket attachments, update files and the copy to
  a new backup location now stop when the disk reaches its reserve, the same as backups and images, and each one says
  why.
- The Server Console warns at the same point the server stops. The LOW mark on the Status and Backups pages is now the
  server's own reserve (at least 2 GB, or 5% of the disk, up to 20 GB), not 10%.
- One bad backup no longer holds up the nightly check. A backup that fails its check is checked again once per check
  period, and the older backups get their turn. If a backup fails its read-back check, the server raises an alert and
  clears it on the next good check.
- Backups stored before 0.93 are quietly re-sealed, one at a time, under their own key. A backup stays readable at
  every step, even if the server stops in the middle.
- Backup pieces are replaced in a single step, so a stop at the wrong moment cannot leave a piece missing. The daily
  database copy is written under a temporary name first and takes its real name only when it is complete.
- A NAS that restarts or drops the server's sign-in is signed in again and the read or write is repeated. A NAS that is
  switched off no longer slows other backup work.
- S3 works without the "list bucket" permission. A key with PutObject, GetObject and DeleteObject is enough.
- The Backups page shows the server's own warning when a setting could not be saved. If your shop's default backup
  allowance is 0, the Server Console asks you once whether to set one; with 0, customer uploads are refused.

### Restoring the server database

- Restoring a database snapshot now puts it back exactly as it was taken. The next server program upgrades it, so a
  failed check never touches your live data. Restore offers "Database snapshot (*.db)" files directly.
- A database restore lists any old file it could not remove.
- If the server cannot tell whether it is already running, changing the data folder or removing card numbers now
  refuses instead of going ahead.

### Backups from the technician console and the customer portal

- Every backup is filed under its customer. Back Up File... and Back Up Registry ask which customer it belongs to, with
  the current ticket's customer picked first; the automatic backup during a run is filed under that run's customer.
  When a backup is filed as the shop's own, the job says why.
- A registry backup that fails to upload is kept in a locked folder for Retry. A skipped automatic backup says so in
  the run's log, and an empty registry backup is no longer offered as a backup.
- Folders left behind by an interrupted Encrypt or Open show in the image library, marked as leftovers. They are never
  deleted on their own; Remove deletes them securely.
- The customer portal's Back up and Download are no longer cut off by an automatic restart. Pressing "Back up files to
  my shop" again on an unchanged folder resumes an upload that was cut off. A customer's Backups page also lists the
  backups your shop made of that PC. Refused or interrupted uploads no longer leave files behind.

### Disk images, erasing and USB sticks

- Capturing and restoring an image shows real progress and time left. Each part of an image is checked and held
  unchanged from the check until it is used.
- If you run the restore script yourself, it refuses the disk this PC boots from, every time. An internal disk needs
  -OverrideDisk naming that disk; a dry run tells you so. Restores started from the console work as before.
- When you erase several drives together, the list of disks is read once just before the first write, and read again
  if more than 30 seconds pass before a drive starts.
- Before the USB writer clears a stick, it checks the disk is still the one you picked (same identity and size). If not,
  the write stops and nothing is erased. A disk that does not report an identity is refused.

### Tickets, messages and customers

- Every ticket has its own number. If two tickets ever shared a number, the later one is renumbered on update and the
  change is recorded in the audit log.
- Older messages remember whether the customer or your staff wrote them, even after a staff account is removed.
  Saving a customer's phone numbers or addresses is all-or-nothing.
- A reply sent twice because the network dropped is posted once. Each file on a ticket has a "Share with customer" /
  "Make shop only" button, and a file already on the ticket is not stored twice.
- When the Service desk list has no match, "Search all tickets on the server" searches by number, customer, subject or
  device. If your shop server is older than v0.443.0, the Service Desk tells you once per sign-in that it gives no
  ticket alerts.
- If your sign-in lapses, the console says "Ticket alerts are paused - sign in again" once, and says when they are back.
- On the customer console, an older shop server shows "Messages are not available from your shop yet" instead of a
  technical error. Messages and the portal open once, and the reply box shows a counter near its limit.
- The customer export also includes the people on the account and a record of the emails sent to the customer. The
  shop privacy notice template lists what the export holds.

### Technician console

- Data Recovery keeps the PC awake until the job ends. Create system image, Create restore point and the driver backup
  and restore run in the background and say when they end and whether they worked.
- Pictures in report and log folders open inside the console; PDFs open in your own PDF app from a private copy.
- Undo will not put a browser's settings back while that browser is open.
- Reports from an earlier shop or visit are no longer attached to a new ticket by themselves; On this PC lists them
  with a Confirm button. Work records refused while you were signed out are sent when you sign in again. A new run is
  refused while an interrupted run is waiting to resume.
- Team chat no longer freezes the window. Cancelling a visit works the same from the booking window and the Schedule,
  and the booking window has "New ticket for this customer". Apps installs, updates and removals are recorded on the
  ticket. Long notes are refused with a clear message instead of being cut short.
- In remote sessions, the technician name shown to the customer is the name the connection was approved under.
- BitLocker: the run names every encrypted drive, including one with no recovery password.
- The run record shows the profile you picked. The report and the undo list always agree. Clock-sync checks work in
  any Windows language. The report says whether the maker's tool or Windows Update installed the drivers.
- Four more Windows Fixes save what they change first, so they can be undone.
- Data migration: the Old PC no longer says apps were reinstalled, and a new Pause button lets you pause and resume a
  transfer (the new PC waits 10 minutes after a pause).
- The address-lookup window says exactly what each lookup sends. The Prep stage caption and the registry backup
  message describe what is actually saved.
- Program search and install read winget on Windows in any language.

### Server Console and shop server

- The Server Console streams a new server program to disk and only gives up when no data arrives for 60 seconds. The
  update messages say what really happens, including the database copy saved in db\update-rollback first.
- Pulling a new release runs in the background, so the server keeps answering consoles. Only full-access
  administrators can start one, and only one runs at a time.
- Saving the server's protected settings, settings files and branding files can no longer be broken by a crash or a
  second save at the same moment.
- Settings has a "Shop app cache" row with its size, its files and an Empty cache button.
- When the server refuses an account change, the Users page and the technician console show the server's reason.
  After a server restart, saving the Square settings tells you if the pairing was lost.
- The daily AI limit counts only calls that got an answer or used tokens, and two people at once cannot pass it.
- The "machine offline" alert rule fires on its own when a machine stops checking in.
- A PC connected over a secure web connection is treated as off-site. The status page stays responsive while it checks
  the firewall.
- RepairShopr import: customers with the same name get a tie-breaker, re-importing keeps names you already have, and
  failed rows are listed with their reason. ABC stock classes value each part at what it actually cost.
- Reprinting a signed form whose stored PDF is missing now tells you so.
- Three old upload commands no client used are retired. Large files are checked without being loaded whole into memory.
- The fleet diagnostic feed now includes attention reports, connect times and long operations.

### Updates and installing

- An update no longer restarts a PC in the middle of a maintenance or resumed repair run. After an update, the console
  restarts from the installed program in every case.
- A PC that cannot reach the shop server waits longer between tries (up to 15 minutes), and About shows the next try.
- A download that fails its check is reported from every pass, so a bad release is held back for every PC. The agent
  confirms an update only after it has started properly; a build that fails to start is rolled back.
- A restart countdown never cancels a restart that another program already started.
- Installing over a running TronForged now works, and the installer tells you the PC's role and version. The shop app
  cache is used only for apps installed for the whole machine.
- The checks we run before every release are more reliable, and releases are checked in full on our own build machine.

### What to do

- Server still on PostgreSQL: move it with TronForged v0.463.0 or older before you install this release.
- Take a database backup, then update the shop server first, then the consoles. Going back to an older server needs the
  copy taken before the update.
- If you store backups on S3, the key needs PutObject, GetObject and DeleteObject. The list permission is optional.
- Check the LOW mark on the Backups page, and set a default backup allowance on Customers & fleet if you have none.
- Close Chrome, Edge or Brave on the customer's PC before you undo a run that changed browser settings.
- If you use your own copy of the shop privacy notice, compare it with docs/SHOP_PRIVACY_NOTICE_TEMPLATE.md.
- If you run restores by hand onto an internal disk, add -OverrideDisk with that disk's number.
- If you re-import from RepairShopr, check the summary for rows it names as not imported.
