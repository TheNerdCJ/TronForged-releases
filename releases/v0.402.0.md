## v0.402.0 - BitLocker is disclosed, and a disk is cloned in one job

**The imaging tool now says what it does with an encrypted drive, refuses one it cannot read, and
clones this PC straight onto a replacement disk - the SSD-upgrade job - in a single run.**

### BitLocker

Windows 11 24H2 encrypts most clean installs by default, so the machine on the bench is usually
encrypted whether or not anyone chose that. What that means for an image was never said. Now it is:

- **A locked volume is refused before anything starts.** If a drive is BitLocker-encrypted and
  locked, Windows cannot read its files and neither can TronForged. The capture stops with a plain
  sentence and the manage-bde command that unlocks it. Before this release a locked drive simply
  vanished from the source list, and a locked second volume failed inside the snapshot with the
  wrong message.
- **An unlocked encrypted volume captures - and the image says so.** BitLocker works below the file
  system, so an unlocked drive presents its files in the clear and that is what the image holds.
  The finished capture states it: the .tfimage is plain text, store and send it accordingly, and a
  restore from it produces an UNENCRYPTED drive. The same sentence appears in the restore plan and
  on the finished restore. Every other imaging product on the market behaves this way; this release
  makes TronForged tell you.
- **Which state a volume was in is recorded in the image** and shown in the image's details, so a
  technician restoring an image weeks later knows the drive comes back unencrypted and that the
  customer's old recovery key no longer applies.
- Where TronForged cannot tell (no BitLocker on that edition, or the check is not permitted), it
  says it could not tell and treats the image as plain text rather than guessing.

Turning BitLocker or Device encryption back on after a restore is a step for the technician, and
the notes say so. On 24H2, a machine signed in with a Microsoft account may turn Device encryption
back on by itself and upload a new recovery key to that account - check before hand-back.

### Clone to disk

**Clone to disk...** on the Imaging tab captures this machine and restores it onto the disk you
choose, in one job: a fast capture to the image folder, the dry-run plan, the same typed
confirmation a restore demands (it names the source, the target, and everything the plan says -
volumes sized down to fit, the recovery partition, the encryption state), then the restore, then
the staging image is deleted. The target is erased; this PC's own Windows disk is read through a
snapshot and is never offered as a target. A clone is always of this PC: if the source list is
set to an external drive, the button says so and does nothing, rather than cloning the wrong
machine.

Two things are checked before an hour is spent capturing: that the chosen disk can hold this
machine even with every volume shrunk to what it holds, and that the image folder is not on the
disk about to be erased. If the restore half fails, the captured image is kept - it is a valid
backup of the machine - and the message says where it is.

A clone is a capture and an apply, not a file copy: Windows depends on hard links inside its
component store that a file copy silently multiplies. Cloning goes through the same image format
as everything else for that reason.

### Worth knowing

Nothing here has run on real hardware. Cloning is proven on the bench only to the point the
scripts can be driven without a disk; the first real clone, the first locked-drive refusal, and
whether Windows re-arms encryption after a plain-text restore of its own image are on the bench
plan by name.
