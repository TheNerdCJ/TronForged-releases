## v0.401.0 - the recovery partition comes back, and a smaller disk is laid out to what is in use

**Two things a restore could not do before this release: put the Windows recovery partition back,
and land on a disk smaller than the one the image came from.**

### The recovery partition

Every Windows machine carries a small recovery partition after the Windows partition. It holds
the Windows Recovery Environment - the thing behind Reset this PC, Startup Repair and the
recovery screen you get when Windows will not start. Until now an image never captured it, a
restore recreated it empty as an ordinary data partition, and nothing told Windows where it was.
The restored machine booted, and its recovery tools silently did not work.

Now:

- **Capture** images the recovery partition as its own part, next to the Windows volume. It has no
  drive letter, so the capture gives it one for the duration and takes it back afterwards; nothing
  about that letter is written into the image.
- **Restore** puts the part back, registers it against the restored Windows (the same command
  Microsoft's own deployment tools use), and then marks the partition as a recovery partition -
  hidden and required - the way Windows expects to find it. The marking happens after the files
  are written, because Windows will not let a partition be marked while it is being written to.
- **Older images** that have no recovery part are handled too: if the restored Windows has a staged
  copy of the recovery environment, it is used to rebuild the partition; if not, the restore says
  plainly that Windows RE was not restored, instead of leaving the partition empty without a word.
- **One step may remain on the restored machine.** Registering the location is done offline; turning
  Windows RE on is a command Windows normally runs once during setup. After the first boot, run
  `reagentc /info` - if it reports Disabled, run `reagentc /enable` once. The Re-register Windows RE
  fix in the toolkit does exactly that.
- On a BIOS/MBR disk the recovery partition is now recognised too; before this release it was
  filed as a data volume on those machines.

### A smaller disk

Before this release the fit check measured the source disk's layout, not what was on it. A 1 TB
drive with a 500 GB second volume holding 20 GB was refused onto a 500 GB SSD - arithmetic that was
never wrong about the bytes and always wrong about the answer.

Now, when the target is smaller than the source, every volume that has captured data is created at
what it holds plus 15 percent (at least 512 MB of headroom), Windows still takes the remaining
space, and the system partitions - the boot partition, the reserved partition and the recovery
partition - are never shrunk. The plan lists every volume that was sized down and what it holds,
and the finished restore says how many were. A target that cannot hold even the shrunk layout is
still refused before anything is erased, with the real numbers.

On a disk the same size or larger, nothing changes: the layout is the source's.

Also in this release: a restore now refuses, before erasing anything, a target disk that holds the
image folder it is reading from.

### Worth knowing

Nothing here has run on real hardware; it is proven on both PowerShell engines and both .NET
runtimes against the real scripts, with the disk never touched. The bench plan carries the items:
a restored machine reporting Windows RE Enabled, and a 1 TB image landing on a 500 GB drive.

BitLocker detection and disk-to-disk cloning are the next release.
