# v0.484.1 - TronForged 0.484.1 - Windows Server manager and update fixes

## TronForged 0.484.1 - Windows Server manager and update fixes

### Windows Server management

- Windows Server actions now work from the fleet on every enrolled server. A server whose remote
  session is hosted by the console itself (the usual setup) used to ignore the request, and the page
  waited up to 15 minutes; it now runs the action and answers straight away.
- A technician who is only watching a session (another technician is in control), or who is in a
  one-time support session, now gets an immediate "not available" answer instead of a page that waits.
- Every change that cannot be undone now needs the exact name typed to confirm it - deleting a local
  or domain user, a group, a computer or a virtual machine, as well as the cluster changes that already
  asked for it. Typing "yes", or the name in different capitals, is refused.
- Turning off "highly available" for a clustered virtual machine removes it from the cluster, so it
  now asks for the VM's name to be typed too. Turning it on does not.
- Deleting a virtual machine from the Make a change form shows a "Back up the VM before deleting it"
  box, ticked by default, with a folder for the backup. The delete does not start until a folder is
  chosen or the box is unticked.
- Move a VM onto the cluster: the backup page no longer promises a default folder that does not exist.
  Choose a folder on the Hyper-V host for the backup, or untick the backup.
- Move a VM onto the cluster: after a live move (the VM keeps running while it moves) the wizard no
  longer asks you to keep or remove an "original" - there is none left on the host. It says so and
  finishes once the VM is confirmed running on the cluster.
- The Windows Server tab now follows what changed: after installing the helper, or once the shop
  server connects, the tab and its page update the next time you open it, without restarting the
  console. Signing in no longer pauses while Windows is asked which server roles are installed.
- Set up a cluster: the list of servers now shows only the customer's own servers - never another
  customer's server that happens to have the same name - and it is read from the shop server when the
  wizard opens, even if the Fleet page was not opened first.
- Windows Server actions no longer wait behind the remote screen. They now have their own connection to the TronForged helper service, so an action no longer fails with "needs the SYSTEM helper" while a technician is watching the screen, and a long export no longer freezes the picture, the mouse or a UAC prompt. If several actions are already running, you are told the helper is busy instead of being told it is missing.
- Moving a VM onto a cluster with a planned move now works between two servers: the temporary export is written to the cluster node's shared volume, which both servers can reach, and it is always removed afterwards, even when the move fails. The move also checks there is room for both the export and the imported copy before it stops the VM.
- Long steps (exports, imports, live moves, cluster checks) get up to two and a half hours each, inside one time limit for the whole action that the console waits for. If a step runs out of time, the result now says the outcome is unknown and asks you to check, instead of saying the VM was left untouched.
- Every detail of a Windows Server action is now part of its authorisation: the group member, the organisational unit, the cluster node, the power action (start or turn off), the cluster nodes and disks. An authorisation for one of these cannot be used for another, and the shop's audit log shows those details.
- The result of each action is now signed by the server that ran it. The shop's audit log records it as done or failed only when that signature checks out, records one result per action, and marks a result that never came back from the server (for example after a lost connection) as unconfirmed.
- Deleting a clustered VM now finds the node that actually owns the VM, and checks the VM is there and its disks are known, before anything is removed. Only disks on a Cluster Shared Volume are deleted; any others are kept and listed in the result.
- After a move, the clean-up step refuses to treat the original server as the cluster node, and only goes ahead once the copy on the node is a clustered VM.
- Preparing another server for a cluster now installs Failover Clustering on that server, not on the one you are working on, and a failed install is reported with its reason. A server that was just prepared can be checked and used for a new cluster straight away.
- Error messages from PowerShell 7 now show the reason itself instead of raw "#< CLIXML" text, and names with accents (such as Jose with an accent) come back correctly.
- Every follow-up step is now checked and reported: a VM that moved but could not join the cluster, a VM that could not be started after a move, an original that could not be restarted after a failed move, and a user created without "must change password at next sign-in" are each said plainly.
- The clock check is more forgiving: an authorisation still works when the server's clock is up to 5 minutes off the shop server's, and it can still be used only once.
- Real names are accepted: CONTOSO\Domain Admins, SRV01\bob, o'brien, names with accents, OU=R&D and VM names such as "Web (prod)". Names are still refused when they hold control characters or the wildcards * ? [ ], start with a hyphen, or are too long.

### Updates

- An update that cannot open its main window no longer marks itself as healthy. TronForged now treats an update as good only once a real window has come up (the sign-in window, the console window, or the required-components page), so a broken build rolls back by itself. Closing the sign-in window twice no longer rolls back a good update.
- A check for updates no longer spoils an update that is already downloaded and waiting. Each release now downloads into its own file, and TronForged does not download a version that is already waiting, already installed, or already applied by the background service. Before this, a good release could be reported as "failed its checks" and held back for the whole fleet.
- When the background service installs an update, it no longer reports success at the moment of the swap. It reports success only after the new version has started properly.
- The background service no longer restarts itself onto an update while a Windows fix is running on the PC. It waits for the fix to finish.
- Installing an older copy of TronForged over a newer one now asks first, naming both versions, and the answer defaults to No.
- PCs no longer all check for updates at the same moment. The first check waits a random extra 0-30 minutes, each later check varies by up to 20 percent, and a check that failed because the shop server could not be reached (or said it was busy) tries again sooner, waiting a little longer each time.
- A console that is behind the program on disk (for example after the background service updated it) no longer downloads the same update again or shows it as "still on its trial run".
- Updating from a USB drive now warns you if a long job is running (a disk image, a service run, a backup transfer), and defaults to No, like Install now.
- A PC enrolled from the command line with an enrolment code no longer applies a waiting update and opens a window instead of enrolling.
- The full-control helper is now replaced as a complete set. If any of its files cannot be replaced, the old set is put back, and the helper is never started on a mix of old and new files.
- Update messages are clearer: a refusal now says "REFUSED:" once, not twice; the background service reports a failed signature check as a signature failure; and if an Install now could not finish, the next time the console opens it says so and why.
- An update now respects the minimum version recorded in the signed release, and the "required update" note comes from the signed release rather than an unsigned field.
- A build that is still with your canary PCs, or that a failed canary report is holding back, is no longer treated as the current version. The fleet's "behind" count, the console versions summary and the Temporary Fleet's support download now use the newest build rolled out to every PC.
- Updating all of a customer's PCs at once now sends each PC the newest build its own update ring allows, instead of refusing every PC because a newer build is still with the canaries. Update now on a single PC still sends the newest build.
- Pausing automatic updates on the Updates page now also stops the server box from updating its own server program by itself, and a version you recalled is never installed over the server program automatically. The Updates page says so.
- The shop server now removes old releases it no longer needs: once a build has been out to every PC for two days, older published and recalled builds are deleted and each removal is written to the Audit log. Builds that any PC could still be offered are always kept.
- The shop server refuses to store a new release when that would leave its own disk nearly full.
- The canary check now always finds a canary's report for the build it is checking, however busy the fleet is. Update reports older than 180 days are removed, and the text a PC sends with a report is kept short.
- A slow download of a new release no longer holds up the server's other routine work (backups, clean-ups and checks), and a download that crawls along without finishing now gives up after 90 minutes.
- When many PCs download an update at once, the server sends to a few at a time and tells the others to try again shortly, instead of running short of memory.
- A shop server with no backup location set can now hand out updates from its own release folder.
- The Status page's release feed row now shows every reason an automatic pull failed (not only an unreachable feed), and the Server Console says why it could not read the feed (for example a rate limit or a refused token) instead of "could not reach".
- A shop using its own release feed now has its server program checked against that feed's own checksum and signature.
- Updating the server program no longer rolls back a new version that is still upgrading a large database. The update waits while the server says it is upgrading, and a new version that does not stop is never rolled back underneath itself.
- The Temporary Fleet support download no longer keeps a copy of the whole program in the server's memory, and a passing read error no longer leaves the page saying there is no program until the next release.
- Restart now on the server box no longer starts the new version while a server operation is still running.

### Licence and privacy

- The privacy notice (section 4.1) now says that the shop's server records the details of each Windows Server management change (for example the member added to a group, the organisational unit or the cluster node), and whether the server that ran the action confirmed the result.
- The licence (section 12.5) now names one more automatic deletion: from this release, the shop's server deletes each PC's record of how an update went (the versions, the outcome and the short reason the PC gave) once it is 180 days old.
