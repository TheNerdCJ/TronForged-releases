## v0.404.0 - the capture hashes its output once, and stops claiming it read it twice

**A capture used to hash every byte of the image it had just written, twice. It now does it once,
and it says honestly what it checked instead of announcing a verification pass that no longer
runs.**

### What changed

A finished capture used to compute each part's checksum, then immediately re-read the whole image
and compute them all again. Measured, the second pass was not buying what it appeared to: on a
machine with enough memory both passes read the same cached copy rather than the disk, and on a
machine without enough memory both passes read the disk in full. There was no case where the
second pass looked at anything the first had not.

It is gone. What remains is the part of that step that was doing real work, and which costs
almost nothing: the finished capture still reads `manifest.json` back off the disk, re-derives its
integrity chain, and confirms that every part file and every split file is actually present. A
manifest that was mangled on its way to disk, or a part file that did not land, still fails the
capture exactly as loudly as before.

**Nothing that uses an image trusts it blindly.** Every path that reads a `.tfimage` still verifies
it in full, byte by byte, first: a restore does it before it erases anything, a clone does it
through that same restore, an upload does it before a byte leaves the machine, a download does it
on arrival and deletes the folder if it fails, Boot in VM does it before it creates anything, and
the Verify button does it on demand whenever you want it.

### The wording is honest now, in three places

The capture used to finish by announcing "Captured + verified". It no longer re-reads the image,
so that would overstate what happened. The finished capture now says what it actually did: each
part was hashed from the bytes on disk as it was written, the manifest was read back and its chain
re-derived, and the full byte-by-byte re-read runs before any restore and on demand from Verify.

Two more places were saying it and should not have been. The status line under the Imaging tab
said the image was captured and verified **on every successful capture**, whether or not the engine
had reported anything at all, and the imaging documentation described the capture as re-verifying
its own output. Both now describe what the product does.

### Worth knowing

Nothing here has run on real hardware, and the imaging plane as a whole still has not. One
question this release raised could not be answered without an elevated machine and is written into
the bench plan by name: whether the integrity table that DISM writes into every captured image is
worth what it costs, given that the only thing which ever asks to check it is Boot in VM.
