# v0.412.0 - v0.412.0 - a release always has a way out, and an update stops lying about itself

## v0.412.0 - a release always has a way out, an update stops lying about itself, and the fleet stops guessing about the helper

**Three repairs to the update machinery, all of the same kind: something reported success it had not
observed. One of them was reported from the field this week; the other two had been failing quietly
for a month.**

### A release can always be moved forward

A shop reported that the Updates page would not publish, to canaries or to anyone.

The cause was a release stuck in a state nothing could move. Starting an artifact upload writes a
catalogue entry immediately, while the upload itself is held only in memory - so a dropped
connection, a closed console or a server restart mid-upload strands an entry with nothing attached.
Publishing it is then refused, because there is no artifact. Pulling the release again is also
refused, because the check for "do I already have this version" never asked whether an artifact had
actually arrived. There was no way to discard it, and no way to recall a draft.

Now: an entry with nothing attached does not block a re-pull, an interrupted upload does not outlive
itself, and a release that cannot go forward can be discarded. **Discard is allowed exactly while
the server is not serving that release** - and that single rule replaced two pieces of code that
disagreed, which is how a **paused** release came to be served to consoles chunk by chunk while the
console offered to discard it. That is fixed too.

**The answer now appears where you clicked.** Refusals were written above the catalogue heading
while the button was below it, so on a long page the reply was off-screen. Worse, the finished-
releases section was rebuilt closed on every action, so expanding it, pressing a button and having
it fold shut over the reply was the normal experience. It now opens itself when it is holding an
answer for you.

A fully settled catalogue also used to render as a single grey button with no explanation, which
looked exactly like a broken page. It says so now.

### An update stops reporting itself as healthy when it was not

Two separate defects, both silent for a month.

**A rollback worked exactly once per machine, ever.** Rolling back renames the failing build aside
and then deletes it - but that file is the program still running, so the delete is refused, and the
refusal was discarded. The leftover then collided with every later rollback, which gave up. Seven
consecutive updates on one machine recorded the same failure line, and nothing read it.

**And the rollback was being reached on healthy builds.** A single start was counted twice, because
the two halves of the program each counted it and the hand-off between them returned the count too
late. So the leftover file was, by accident, the only thing preventing every good update from being
undone. Both are fixed, in that order, which matters: repairing the leftover alone would have turned
those harmless log lines into real rollbacks.

**A refused rollback is no longer recorded as success.** It used to delete the marker and the
last-known-good copy and write "health confirmed", then tell the server the update had applied -
which releases the brake that is supposed to hold a bad rollout. The verdict is now written down
when it is decided, and a health confirmation only speaks for the attempt it belongs to.

### The fleet stops guessing about the sign-in screen

A console reported that a machine had UAC and sign-in-screen control whenever a pipe of the right
name existed and a service was running. Neither proves the real helper is the thing answering.

It now reports what it actually verified, and **"could not check" is a real answer** rather than
being rounded to yes or no. A machine whose helper this console could not confirm reads "not known -
this PC could not check", which is different from a machine nobody has heard from.

The console also stopped re-dialling the helper on every heartbeat, which was writing the same
"connected" line to the log around fourteen hundred times a day.

### Worth knowing

**One narrow case is left open, deliberately.** Two console starts within about three seconds of
each other, during the short window after an update lands, can still undo that update. The result is
a revert that the next update check re-applies. Closing it properly means changing where a launch is
counted, which is a design decision rather than a repair, and it is recorded as such.

**Nothing here has run on real hardware.** The rollback ordering, the discard and the capability
reporting are all proven against fixtures and a throwaway server.
