# v0.398.0 - v0.398.0 - remote desktop rides the web transport (orange cloud supported)

## v0.398.0 - remote desktop rides the web transport

**Remote control now works for machines that reach the shop over the web transport
(WSS), which makes a Cloudflare-proxied ("orange cloud") DNS record a fully supported
setup - including remote support.**

### What was wrong

The server has offered a second door since v0.279.0: ordinary HTTPS + WebSocket, for
machines on hotel, campus and guest networks that block custom ports, and for shops that
want Cloudflare's proxy in front of their address so the shop's own IP stays out of
public DNS.

Every part of the product could use that door except one: remote control. A machine
that came home over the web transport showed up in the fleet, reported, patched and
backed up normally, but the Remote control button was off, with the reason "reaches
the shop over the web transport, which cannot carry a remote session yet". Under an
orange-clouded record that is every off-site machine, so remote support was effectively
LAN-only for any shop using the proxy.

### What changed

The rendezvous that carries a remote session now moves bytes over the web transport
exactly as it does over the direct port. Both ends can be on either door - a customer
PC on WSS and a technician on the direct port, or the reverse - and the session is the
same end-to-end encrypted stream in every case. The server still sees only ciphertext;
so does the proxy.

- The fleet tile no longer treats "reached us over the web transport" as a reason the
  button is off. If the machine is armed and checking in, Connect works.
- The technician console's connection deadline applies over the web transport too
  (before this release it silently did not).
- A remote session that ends over the web transport ends cleanly on both sides.

Behind the proxy, two things are normal and are handled: Cloudflare drops a connection
that carries nothing for 100 seconds on Free/Pro plans - the server pings every
45 seconds, which counts - and it closes every open WebSocket when Cloudflare deploys,
a few times a day. A session cut that way ends on both sides, the machine parks itself
again, and Connect works as before.

### How it was verified

Two automated proofs run on every build: one parks a machine, joins a technician and
pumps bytes through the server with every byte a WebSocket frame on both legs; the
other does the same through the console's own connection code on a profile whose
direct port is dead. The first of them caught a defect during development - the server
was closing a parked machine's connection the moment it parked - which is why this
release exists as one change rather than two.

### Worth knowing

- `docs/SERVER_SETUP.md` Part G step 5 describes the setup: `wssPort` on one of
  Cloudflare's proxied ports (443, 2053, 2083, 2087, 2096, 8443), an Origin CA
  certificate pair, the same port forwarded on the router, then the record may be
  flipped orange.
- Nothing in this release has run on real hardware yet; the bench plan carries the
  item. Everything is proven on loopback against the real server and the real console
  code.
