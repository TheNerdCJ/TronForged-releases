# v0.409.0 - v0.409.0 - the Remote tab is the fleet and the session

## v0.409.0 - the Remote tab is the fleet and the session, and an armed PC stops overstating itself

**The Remote tab carried five things; a technician needed two of them. The manual support-code
connection is retired, the settings that configure this PC moved to Settings, and a machine that is
armed but cannot actually be reached now says so instead of reporting itself ready.**

### What the Remote tab is now

Your unattended fleet, the machines waiting for approval, and the live session with the controls
that drive it. That is the whole tab.

Remote control from a fleet tile still lands here and works exactly as before.

### What moved to Settings

The things that configure **this** PC rather than doing remote work: unattended access and its
policy line, the agent's status, the off-site route test, and the full-control helper that gives a
technician the sign-in screen and UAC prompts.

They kept the permission they had. The block is hidden from anyone whose session does not hold the
remote permission, exactly as the tab was, and it comes back the moment the permission is granted.
That was a real risk in a move like this and it is checked on the built program rather than assumed.

### What was removed

**Typing a support code to connect to another PC, and scanning the network for one.** With it go the
one-time support code and the button that armed a PC to hand one out.

This is a deliberate narrowing. **The unattended fleet is now the way you reach a machine.** A PC
that is not in the fleet cannot be connected to, and the way a machine joins is approval enrolment:
it shows six digits, somebody reads them to a technician, the technician matches them.

The fleet dashboard used to suggest pairing with a support code when it could not find a machine.
It now names what actually works.

### An armed PC now tells the truth about whether it can be reached

This is the part worth reading even if the rest does not affect you.

"Armed" and "reachable through your shop" were being treated as the same thing, and they are not. A
machine can be armed, enrolled, and still hold no unattended access - and three separate places
reported it as ready anyway. One of them would keep saying a machine was waiting at the shop server
for the rest of the day after that access had been withdrawn.

All three now ask one question with one answer, and a machine in that state says plainly that the
shop cannot reach it. A machine that stops offering itself also records why, once, rather than going
quiet and leaving nothing behind.

**You may see this on a technician console** that has automatic arming switched on but never joined
the fleet. That machine has always been unreachable. The only new thing is that it admits it.

### Repeated bad connection attempts do something again

Eight failed attempts used to rotate the support code. With no code left to rotate, that protection
would have quietly become nothing.

Instead, a machine now refuses new connections for a window that doubles each time up to half an
hour, records why, shows how long is left, and clears the moment a real connection succeeds. A
connection that arrives with no unattended access at all is refused outright rather than being
allowed to try.

### Worth knowing

**A shop that changed its agent port keeps it.** That port was being read from a box on the deleted
panel, and it is also what your before-login service binds to and what the firewall rule is opened
for. It now comes from your saved settings, and a shop on a custom port was verified end to end -
the console, the before-login service, the repair loop and the firewall rule all still agree on it.

**None of this has run on real hardware.** No technician console, no customer PC, no fleet tile
clicked on a live shop. It is proven by constructing the real windows from the shipped program and
reading back what they render.
