# v0.446.0 - Tray alerts for customer requests, stricter access rules and safer backups

This is the first release on the feed since v0.442.0, and these notes cover everything since then. v0.443.0, v0.444.0 and v0.445.0 are added to the release page for the record only: they are not offered as updates, and shop servers, consoles and new installs go straight from v0.442.0 (or older) to this release.

In short:

- A technician console shows a tray alert when a customer asks for help or answers on a ticket, even while it is minimized.
- The Server Console tells you when the shop server is using a settings change that it could not save to disk.
- The shop server is stricter about who may do what, above all for logins linked to a customer and for administrators who manage other accounts.
- Backups can no longer fill the shop server's disk, and a new shop server starts with no backup allowance until you set one.
- Technician consoles install their own updates when idle again, and more long jobs hold off an automatic restart.
- A round of fixes: **Stop Safely** stays on screen, **Choose machine...** works (for reception too, once the shop server has updated), the report of a run that restarts the PC reaches its ticket, **Install helper** replaces an out-of-date helper, and a rename is no longer undone by an older copy.

This release updates the consoles and the shop server's program. If your shop server is already on v0.442.0, it does not change your shop's database. Read **Before you let your shop server take this update** first.

### Before you let your shop server take this update

- **Check which logins are linked to a customer.** From this release, a login linked to a customer record is that customer: it sees only that customer's own tickets, invoices and backups, and any staff permissions its groups give it are ignored while it stays linked. On the server PC, open the Server Console, go to **Users & groups** and click **Edit** on each login. If a login that belongs to someone who works for you shows a customer under **Linked customer**, set it to *Not a customer (staff account)* and save. Once the server runs this release, it refuses to unlink a login in a save that keeps its staff groups: untick those groups, set *Not a customer (staff account)* and save, then click **Edit** again and tick them back. If an administrator's own login turns out to be linked after the update and can no longer manage accounts, use **Set up server > Create / reset administrator...** at the server PC with that login's username and *Reset if this administrator already exists* ticked: it sets a new password, gives the login its administrator rights back and removes the link. After the update the page also marks linked logins for you (see **After you update**).
- **Servers set up from the Server Console before this release: set a shop default backup quota.** Those servers were set up with an unlimited default, and updating does not change it. On **Customers & fleet**, with no customer selected, press **Change default quota...** under *Shop-wide* (on such a server the line above the button may keep saying *loading...*, and the dialog opens on *Unlimited*), choose *Capped at:* and enter a size in GB. The quota counts everything filed under a customer, including disk images a technician uploads for that customer, so allow for those. A customer's own quota (**Backup quota...** on that customer) still comes first.
- **If your shop server is older than v0.442.0** (the Server Console's **Status > Server program** shows its version), the first time the updated server starts it adds to your shop's database, as v0.440.0 and v0.442.0 do, and after that no older server version will open it. Going back would mean putting back a copy of the database made before the update, together with the older server program, and losing everything entered since. The Server Console cannot do that for you: its **Restore database...** always uses the server program that is installed. To keep that possibility open, make a copy straight away - a shop server updates itself soon after a release, and a Server Console that has just started may update it after about a minute and a half: on the server PC, open the Server Console, press **Settings > Database maintenance > Back up database...**, then update by hand (see **After you update**). The server also copies its database once a day into `C:\ProgramData\TronForged\server\backups\db\` on a standard install (the folder needs administrator rights) and keeps only the newest seven; if an update starts first, copy the newest one made before it somewhere safe. Neither kind of copy is encrypted: each holds every customer, ticket and invoice and the credentials of every enrolled console, so keep it somewhere only you can reach.

### After you update

- **Update the shop server by hand if you can:** on the server PC, **Server Console > Settings > Updates for this PC > Update everything on this PC**. Most of what this release changes is decided by the shop server and applies only once the server has updated (see **While the consoles and the shop server are on different versions**).
- **Open Users & groups again.** With the server updated, the page marks two kinds of login:
  - *linked - staff permissions ignored*, with the permissions the login no longer gets. If it belongs to someone who works for you, unlink it as described above, or give that person a separate staff login.
  - *not linked - its email matches ...: link it*. Link it to that customer. If it belongs to a member of your staff rather than that customer, change the customer's contact email so the two no longer match.
- **Tidy your customers' logins.** Every login a customer uses should be in the **Customers (portal)** group only, with its customer chosen under **Linked customer** - a customer's login that is not linked may now be told so when it looks for its invoices. Open the **Customers (portal)** group too: it should hold only tickets and backup. If it holds anything else, untick the rest and save; only an administrator with full access can.
- **Technician consoles that have been used for remote control may not install this update by themselves.** Until this release, once a technician console had started a remote-control session - even one that never connected - it stopped installing its updates when idle until TronForged was closed and opened again. This release fixes that, but the fix arrives with the update. On such a console, go to **Settings > About**, press **Check for updates**, then **Install and restart** when it appears.
- **Before a long Data Recovery job, install this update on that console first,** the same way. The restart protections below apply only once a console runs this release; the update that brings them is still installed under the old rules. If the restart countdown appears during a job, press **Not now (1 hour)**. Data Recovery does not keep the PC awake, so set the PC not to sleep while a long job runs.

### Tray alerts when a customer asks for help

- **A technician hears about it, minimized or not.** Every technician console signed in with an account that can manage tickets (tickets.manage) asks the shop server once a minute and shows a Windows notification when a customer opens a ticket - with **Request support from a technician** in their PC's tray, or through their shop account - or answers on one.
- **What it says:** *New support request #41*, with the customer's name and the ticket's subject, or *Customer replied on #12*; the priority is added when it is high or urgent. Several at once become one alert that says how many and names the most urgent. Click the alert to open that ticket in the Service Desk.
- **What is not announced:** tickets booked at the counter or created in the Service Desk, staff replies and internal notes, and anything that was already waiting when the console signed in - that is in the Service Desk list.
- **Every such console gets every alert,** not only the technician the ticket is assigned to, and there is no setting to turn them off. Each alert shows a customer's name and ticket subject, so it also appears on a front-desk PC signed in with such an account. The Server Console does not show them.
- **Never on a customer's PC,** even while a technician is signed in there with **Technician sign-in...**.
- **It needs the shop server on this release.** Until the server updates, the console stays quiet and says nothing about it.

### Who may do what on the shop server

- **A login linked to a customer is that customer, whatever groups it is in.** It sees only that customer's own tickets, invoices and backups. Any staff permissions its groups give it are ignored while it stays linked, so it can no longer reach other customers' records, invoices, machines or remote access, the shop's billing, or the team chat. Customers using their own shop account notice nothing.
- **A login the shop server cannot place with any customer** is told that its account is not linked to a customer record when it asks for invoices, instead of being shown an empty list.
- **Administrators who manage other accounts.** An administrator without full access can no longer edit, link or unlink, reset the password of, delete, or revoke the sessions of an account that holds full access or a permission it lacks itself, and it can change only the groups whose every permission it holds. Only an administrator with full access can change the permissions of the built-in **Administrators** and **Customers (portal)** groups; Administrators always keeps full access, Customers (portal) can hold only tickets and backup, and neither group can be deleted. **Create / reset administrator...** at the server PC also gives the Administrators group its full access back if it was removed.
- **An administrator's change sticks.** A password reset, demotion or customer link can no longer be undone by that account signing in, refreshing its session or changing its own password at the same moment. **Revoke all sessions** (Users & groups > **Sessions**) and a change to an account's groups are now written to the audit log.
- **Team chat stops at once** for a login whose sessions are revoked, whose password is reset, that is demoted or linked to a customer, or that signs out. It no longer keeps receiving messages until its connection drops.
- **Server settings from another computer.** The release feed and the automatic-update switch, the AI settings, a customer's backup quota and the branding logo and program icon can now be changed from another computer only with the server.manage permission, like the server's other settings. At the server PC nothing changes.
- **Windows updates on customers' machines.** Listing a machine's update commands, queuing an update check, approving updates and changing the update hold list no longer rest on the patch permissions alone: an account that is not staff (staff hold tickets.manage or users.manage) reaches at most its own customer's machines and rules, never another customer's, and cannot hold updates back for the whole fleet. Give patch and patch.approve to staff only.
- **Draft customer summary sends less.** The shop server removes the customer's name, the ticket number and the report's location from the request before anything reaches the AI service, whichever console sends it.
- Further security work is under way and will follow in the next releases.

### Backups

- **A new shop server starts with no backup allowance.** On a shop server set up with this release, nothing can be backed up under a customer - neither the customer's own backups nor a disk image a technician files under that customer - until you set a shop default quota (**Customers & fleet > Change default quota...**) or that customer's own quota (**Backup quota...**). Until then the upload is refused with *The shop has not given this customer any backup storage yet. Ask the shop to set a backup allowance.*
- **Backups cannot fill the server's disk.** Whatever the quotas, the shop server refuses a backup upload that would leave less than 5% of the backup disk free (at least 2 GiB, at most 20 GiB), so backups cannot fill the disk your database lives on. The upload stops with *The shop server's backup disk is nearly full, so this backup was not accepted. Tell the shop.*, and the server's log records how much space is free. Free some space, or move the backups with **Backups > Change location...**. A backup location the server cannot measure, such as cloud storage, is not checked.
- **Only the shop deletes a finished backup.** A customer's own login can no longer delete a finished backup, or any backup your shop made; it can only clear away an upload of its own that did not finish. Old backups are removed by the shop, from the **Backups** page.
- **A delete removes only that backup.** A delete that does not name a backup on the server's list is refused.

### Settings the server could not save

- **A change the server could not write to disk now says so.** A settings change is used by the shop server straight away, but it survives a restart only once it has been written to disk. The **Square** page (and **Pair a Terminal...**), **Email**, the default backup quota and the backup storage location used to report success even when that write failed - so a Square token or mailbox password that never reached the disk was gone at the next restart. Now they say that the server is using the change but could not write it to disk, and the audit log marks the change *[NOT SAVED TO DISK]*. The same pages opened through **Server administration** on a technician console show the same message.
- **The AI settings** (**Settings > AI features**, including the ticks under *What this shop's AI may be used for*) show the same warning. They used to call such a change a failure and set the tick back while the feature was in fact on. The **Branding** page and the release-feed setting also record such a failure in the server's log and the audit log.
- **A new backup location and its share login are written together.** If the server cannot write both, the location and login on disk stay as they were, so a restart never pairs the new location with the old login.
- **The Terminal pairing note** shows its warning in the warning colour, tells you to press **Save** on the Square page, and says the pairing is saved once a later Save writes it down.
- **If you see the warning,** check the free space on the server PC's disk and the permissions on the server's data folder (`C:\ProgramData\TronForged\server` on a standard install, where the service account `NT SERVICE\TronForgedServer` needs Modify), then save the same setting again - for a paired Terminal, press **Save** on the Square page. Do it soon: the server restarts by itself when it installs an update, and a change that was never written down is lost then.
- The warnings need the Server Console and the shop server both on this release. An older server cannot tell, and the pages behave as before.

### Updates and restarts

- **Technician consoles update themselves when idle again.** Since at least v0.431.0, once a technician console had started a remote-control session, it never again installed its own updates when idle until TronForged was restarted (see **After you update**).
- **An idle update waits for long jobs.** A console with an update downloaded restarts itself to install it once the PC has been idle for ten minutes. It used to wait only for a service run, disk imaging and remote sessions. It now also waits for a Data Recovery job (a disk image, file carve or analysis), a forensic collection, a Windows ISO or tool download, the PowerShell 7 install, a network settings change, Windows updates the shop sent to that PC, a fix from the **Windows Fixes** tab (or one run by a technician connected remotely), the **Benchmarks & QC** benchmark, and a backup upload to or download from the shop server.
- **Restart when the PC is next idle** - the shop's choice when it installs Windows updates on a PC - waits for the same jobs, so it no longer restarts a bench PC in the middle of a disk image. **Restart now (60-second warning)** is unchanged: it restarts the PC whatever is running.
- **The countdowns check again.** A job started during a restart countdown now calls the restart off, and a Windows-update restart that was called off waits for the next quiet moment. **Restart now** on the update's countdown, pressed while a job runs, asks first and names the job.
- **Install and restart** (**Settings > About**, under UPDATES), pressed while one of these jobs is running, says which job it would stop, and defaults to No.

### Service Desk, tickets and reports

- **Stop Safely stays on screen.** At the console window's narrowest, **Draft customer summary** could push **Stop Safely** off the edge of the window during a run. **Draft customer summary** now appears only when it can be used, and with a larger UI text size the window's narrowest width grows so the row fits.
- **Choose machine... works.** On a ticket it answered *No such machine.* for every choice; it now links the machine. With the shop server on this release, a reception login can choose the machine too, and a machine whose enrolment was revoked is never offered. If the list cannot be read, it says why instead of saying the customer has no machines. As before, once a ticket names a machine, starting a run for that ticket on a different PC asks *Run here anyway?* first, with No as the default - which now includes a ticket booked at the counter and linked with **Choose machine...**.
- **A run that restarts the PC gets its report onto its ticket.** When the part of a Safe Mode scan or Windows-updates run that resumes after the restart finishes, the console records the final report on the run's ticket (under **Files > On this PC**) and attaches it the way it attaches any run's report - once the console is open with the technician who started the run signed in to the shop server. A tray alert then says *Service finished - ticket #...*. On a customer's PC the report waits until a technician signs in there again, and the customer is shown nothing about it. If a different technician is signed in, the console says so: attach the report by hand from the ticket's **Files > Attach a file...**.
- **More reports are listed on their ticket.** **Files > On this PC** also lists older reports named for the ticket's number that were never recorded against it, such as reports from before v0.434.0 (see **Known issues**). **Attach a file...** opens in this PC's reports folder, and a service report attached that way is listed under **On this PC** too, so the report of a run started without a ticket can get a customer summary.
- **The Reports tab on a customer console** no longer sends the customer to a Service Desk they do not have. It says the reports from a service on this PC are saved on it, and **Open Reports Folder** opens the folder they are kept in. A login on a technician console that cannot open tickets sees the same.
- The **Benchmarks & QC** tab says where **Save QC Report** saves the checklist.

### Remote support

- **Install helper replaces an out-of-date helper.** **Enable UAC / lock-screen control** (in a remote session's **REMOTE CONTROL** panel on your **Remote** tab) and **Install helper** (at the PC, on the **Settings** tab) now put the full-control helper that the PC's own TronForged carries in place of an older one, start it, and say what they replaced. Before, they registered the old file again, so a helper that an update had failed to replace could not be fixed this way. They never put an older helper over a newer one. This needs the PC being fixed to run this release, whichever version your own console runs. At the Windows sign-in screen the request is answered by that PC's background service, which runs this release only once the PC (or its TronForged agent service) has restarted since the update - until then, restart that PC and try again.
- **Ctrl+Alt+Delete after a helper fix.** On a PC that runs this release, when Ctrl+Alt+Delete says its helper is too old, the message names **Enable UAC / lock-screen control**. Once the helper is replaced, the next Ctrl+Alt+Delete in the same session reaches it - there is no need to reconnect. If it still reports the old version, restart that PC and try again.
- **A reconnect keeps your Ticket box.** When a remote session drops and reconnects on its own, the Tech, Ticket and Customer you applied in the **REMOTE CONTROL** panel are kept and sent to the PC again. A new connection still starts with empty boxes, so one job's ticket is never carried into the next.

### Customers and invoices

- **A rename is no longer undone.** If someone renames a customer while you have that customer open, your save keeps their new name, and the form tells you so. This needs both your console and the shop server on this release.
- **Customers imported from RepairShopr are protected from old consoles.** A console older than v0.438.0 sends a customer's whole record with every save, which would put blanks back over what your shop has added since the import. The shop server now refuses such a save or re-import with *Nothing was saved: this console is older than release 0.438.0...*. Update that console (on a technician PC: **Settings > About > Check for updates**; on the server PC: **Server Console > Settings > Updates for this PC > Update everything on this PC**), then save again. Rarely, a console from v0.438.0 to v0.442.0 that changes every field of an imported customer in one save gets the same message; updating it fixes that too.
- **Import customers (CSV)...** (Server Console > **Set up server**) no longer fails row by row against a shop server older than v0.437.0: when the file holds customers that server does not have yet, it sends nothing and says to update the shop server first.
- The Server Console's **Accounting** page now says that QuickBooks files each invoice under the customer's current name and address, while a reprint from TronForged shows the Bill-To the invoice was sent with.

### While the consoles and the shop server are on different versions

Your consoles update from your shop server, and the server updates its own program when the shop is quiet, so for a while some may be ahead of others.

- **Decided by the shop server, whatever the consoles run:** the rules for logins linked to a customer, for administrators who manage other accounts, for server settings changed from another computer and for Windows updates; the team chat cut-off; the backup allowance, the free-space reserve and who may delete a backup; the protection for customers imported from RepairShopr; and what **Draft customer summary** sends. They take effect when the server updates.
- **Need the console and the shop server both on this release:** tray alerts, the not-saved warnings, keeping someone else's rename, the marks on **Users & groups**, and **Choose machine...** for a reception login. Until the server updates, an updated console shows no tray alerts, reports saves as before, and a save from a stale copy of a customer can still put back an older name.
- **Work on each console as soon as it updates, with any shop server:** the restart and idle-update fixes, **Stop Safely**, **Choose machine...** for technicians, run reports and remote reconnects. The helper fixes need the PC being fixed to run this release.
- On a customer's own PC, apart from the backup messages above and the message a login that is not linked may see when it looks for invoices, the only change the customer sees is the Reports tab.

### Known issues

- **Servers set up from the Server Console before this release keep an unlimited default backup quota** until you set one (see **Before you let your shop server take this update**). The free-space reserve protects the disk either way.
- **Tray alerts stop, without saying so, once a console's sign-in with the shop server runs out** - 12 hours after signing in, or somewhat later if the console reconnected in between - and from this release team chat messages that come through the shop server stop reaching that console at the same moment. If a technician console has been running since the day before, right-click the TronForged icon in the notification area, choose **Close TronForged**, then open TronForged and sign in again.
- **Very rarely, a customer's request or reply arrives without an alert.** It is still in the Service Desk.
- **Automatic restarts do not wait for everything yet.** They do not wait for a maintenance run (scheduled, or **Run maintenance now**), for the part of a Safe Mode scan or Windows-updates run that resumes by itself after its restart, or for a customer's own backup upload or download on a customer console. If the countdown appears on a technician console while one of these is running, press **Not now (1 hour)**, and do not choose a restart when you send Windows updates to a PC that is running one.
- **Install helper can report a replacement with the same version number** (for example 0.446.0 -> 0.446.0). This is harmless: the helper is this release's either way.
- **A reinstalled PC can be asked about its own tickets.** A PC that was reinstalled and enrolled again is a new machine to the shop server, so a ticket linked to it before then asks *Run here anyway?* on that same PC. Choose Yes, or use **Change machine...** on the ticket to link it again.
- **Files > On this PC can list an old report under a ticket that only shares its number** - for example a report from before v0.434.0 that was named for a ticket number from another system. Check the customer and the date of an older report before you attach it or draft a summary from it.
- **On Users & groups, a refused change can give the wrong reason.** When the server refuses a password reset, a delete or **Revoke all sessions** (for example because the account outranks yours), the message shown may name another reason, or none. **Edit** shows the server's own reason.
- **While the not-saved warning shows, the Square and Email pages still say a token or password "is saved on the server".** That means the server has it in use; it is on disk only once a save shows no warning. When the server can write only part of a change, the warning also appears for the part that was written. Fix the cause and save again either way.
- **If consoles cannot reach the shop server after it updates** (a server updating from a version older than v0.442.0), open the Server Console on the server PC and press **Settings > Updates for this PC > Update everything on this PC**. Your data is intact. If the updated server is slow to come up - for example while antivirus scans it - the update puts the previous server program back and may say the shop is still online, but that program cannot open the updated database, and the server does not try the update again on its own. This is uncommon.
- **None of the changes since v0.442.0 has been tried on a real shop's hardware yet.** They were tested on the build machine, with the server's own code and its real database engine, not on a shop server or customer PCs. In particular, a restart countdown being called off has not yet been seen on a real PC.
- Still open from earlier releases:
  - **Leave address lookup switched off for now** (v0.441.0). With suggestions showing, Tab moves into the suggestion list, and Escape there can close the customer form without saving; a quick Enter can bring the list back and take the same street in another town; the **Address lookup...** button can be cut off on smaller screens (maximize the Server Console window); a Photon server of your own must be version 1.1.0 or later; and while an address service is slow to answer (up to 8 seconds), everything else that console asks the shop server waits behind it.
  - Unticking **Packages ship to this address** before **Mail goes to this address** can drop a typed shipping address. Untick **Mail goes to this address** first (v0.440.0).
  - After **Edit contact details**, the Service Desk's customer card keeps showing the old details until the customer is opened again from the list. Open it again before editing a second time: a second edit from the old card can remove a mailing or shipping address the first edit saved, and its form may say someone else renamed the customer (v0.439.0).
