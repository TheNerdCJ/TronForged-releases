## v0.407.0 - deleting image backups is a button now, and the confirmation stops guessing

**Clearing old images off a bench PC was hidden in a right-click menu, worked on one image at a
time, and reassured you about the shop server without ever looking. All three are fixed, and the
confirmation now shows you the one image that cannot be recovered.**

### The button

**Delete from this PC...** sits on the image library's row of controls, beside Restore. Every other
action on an image was already a button there, and even the shop server's copy had its own Delete;
the local one was the odd one out, hidden behind a right-click nobody had a reason to try. The
right-click entry still works for anyone who learned it.

Select one image or several, with Ctrl and Shift, and delete them in one pass. The greyed rows - an
interrupted capture, a browse session left open - are never part of a selection, even when you
select the whole list, because neither one is an image.

### The confirmation stops guessing

It used to say a copy on the shop server, "if you uploaded one", was not touched. That is a guess
dressed as reassurance, and the console already knows the answer because the shop server's list is
sitting on the same screen.

Now it looks. The confirmation names every image it is about to delete, each one's size, and the
total space that will come back. For each image it says whether the shop server has a copy, in
**three** honest states rather than two: a copy is on the server; there is no copy, so **this is the
only one that exists**; or the server list has not been refreshed this session, so it says it does
not know rather than implying anything.

**The only copy is drawn, not merely worded.** It sorts to the top of the list, it carries a
coloured rule down its edge and a tinted panel, and its line is bold. It also says so in words, so
nothing depends on seeing colour. In a list of six, it is the line the eye lands on, because it is
the one that cannot be undone.

The default answer is No, and Enter or Escape both keep your images.

### It refuses whole, or tells you it did not

An image is now checked before anything is removed: every file in it must be closed and writable. If
something is holding a file open, the image is refused **untouched**, naming the file responsible -
rather than being stripped down to the one file that would not go and then reported as "refused".
That was the real defect: a recursive delete removes everything it can reach before it hits the
obstacle, so an image reported as untouched had already lost its manifest and would never restore.

For the narrow case that check cannot cover - a file locked in the instant between the check and the
delete - the console reads the folder back and says that image was part-deleted, rather than calling
it untouched, and tells you it now shows as an interrupted capture.

Afterwards it says how many images actually went and **names the ones that did not**, with the
reason. A count alone would leave you in front of the library working out which two of six are
still there.

### Worth knowing

None of this has run on real hardware, and the imaging tools as a whole still have not. No image
has ever been deleted through this dialog by a person.
