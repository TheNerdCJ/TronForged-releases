# v0.403.0 - v0.403.0 - the restore stops trusting what it cannot prove, and captures default to XPRESS

## v0.403.0 - the restore stops trusting what it cannot prove, and two dead ends get an exit

**Four real defects in the imaging tool, two jobs that used to leave a technician with nowhere to
go, and a permission so that restoring a disk is no longer the same grant as taking a backup.**

### The restore refuses a disk it cannot vouch for

Restoring a disk erases it, and the check that stops TronForged erasing the disk Windows is
running from used to give up quietly. If it could not work out which disk that was, it simply
allowed the restore. Now it refuses and says why, and the only case where "I cannot tell" is a
true answer rather than a failure - a machine booted from rescue media, where no local disk holds
the running Windows - is recognised as such.

### A restore could fail without saying anything

At the very end of a restore, TronForged registers the recovery environment on the restored disk.
The tool it uses reports its problems on a channel that, under the version of PowerShell that
ships in Windows, ends a script immediately. The result was a restore that stopped with no
warning, no failure message and no completion message, and a status line that said the wrong
thing. Worse, the same call runs on the success path, so a restore that had worked perfectly could
still end that way. The recovery step now reports what happened either way, and the restore can no
longer end without telling you something.

### Browse says why it cannot open an image

An image captured with LZMS compression is written as a single solid archive, which the Windows
imaging tools can restore but cannot open for browsing. Choosing that option from the capture
screen and later pressing Browse produced a raw error. It now says plainly what happened, that
restoring the image is unaffected, and what to capture with instead if browsing matters.

### Interrupted captures stop being invisible

A capture writes its manifest last, and the library only lists folders that have one. A capture
killed by a power cut, a crash or a hard shutdown therefore left a folder of many gigabytes that
appeared nowhere, could not be removed from the library, and quietly ate the free space the next
capture needed - and retrying made a second one. The library now names each interrupted capture
folder and what it is costing, and offers to remove it. TronForged never removes one by itself,
never touches a folder that has a manifest, and says clearly that a capture running right now
looks exactly the same as an abandoned one.

### The room check runs before you press Capture

The capture used to work out whether there was room only after it had started, so a technician
with a small scratch drive learned the job was impossible several minutes in. The capture card now
shows the same verdict, in the engine's own words, before anything begins. It is still a floor
rather than an estimate: compression is never worse than the figure shown, and the capture checks
again before it writes anything.

### Restoring and cloning need their own permission

Until now the Imaging tab rode a single permission, so "upload a backup" and "erase this physical
disk" were the same grant - and that grant is in the seeded customer portal group. Restore, Clone
to disk and the target disk picker now need a separate `backup.restore` permission. Capture,
Browse, Verify and upload are unchanged and still ride the backup permission, so a customer
self-serving a backup loses nothing.

On update, that permission is granted automatically to the technicians group and to any group your
shop has marked as staff, so nobody loses the feature. It is not granted to the customer portal
group. If a hand-built group needs it, an administrator adds it in Manage users and groups. A
technician working offline picks up a newly granted permission at their next online sign-in.

Deleting an image from the server is destructive but it is backup management rather than restore,
so it stays on the backup permission for now.

### The fleet says which machines have an image

The fleet list now shows, per device, how old its most recent image is and how big. A machine that
has never been imaged says so rather than showing a blank. It reads the shop server's existing
backup catalog, so there is nothing new to configure.

### Captures default to XPRESS now, and the capture tells you how fast it went

The capture compression default changes from LZX to XPRESS. Measured on a 24-thread
workstation, LZX takes about 1.4 times as long as XPRESS for an image about 9 percent smaller.
On a four-core machine, which is what most bench PCs and most customers' machines are, LZX
takes 3.1 to 3.6 times as long. The product had already reached this conclusion once and
hard-coded XPRESS for Clone to disk, calling it the fastest capture; the default now agrees
with it.

LZX, LZMS and none are all still there in the dropdown and all still restore identically. If
you keep images for months, LZX and LZMS still earn their place, and the tooltip now says
honestly what each one costs instead of calling LZX "sensible capture time".

**One consequence worth knowing before you update.** An XPRESS image is bigger, so the check
that decides whether the destination has room asks for more free space: roughly 57 percent
more than it asked for LZX. A capture onto a tight destination that used to be accepted may now
be refused before it starts. That is the honest figure for the larger file rather than a new
restriction, and the refusal names the number it wants. Pick LZX for that job, or a roomier
destination.

**The capture now reports its own speed.** Each stage records how long it took, and the
finished capture states the elapsed time and the rate it actually achieved over the source
volume. The progress footer also shows a rate while the job runs. Until now the imaging tab
could tell you gigabytes written and minutes elapsed and never divided the two, which made a
slow disk, a slow compressor and a busy antivirus scanner impossible to tell apart from the
screen.

### Also fixed

Five sentences told a technician to click a button by a name that does not exist in the product,
including two that named two other buttons on the tab the technician was already looking at. All
five now use the real names, and a new check makes that class of mistake fail the build.

The launch-crash gate could spin without ever finishing when a failure carried a long chain of
causes; it is now bounded, and the build step has a time limit so a hang reports a reason instead
of an exhausted budget.

### Worth knowing

None of this has run on real hardware, and the imaging plane still has not. That is the next piece
of work and it needs a bench, a spare disk and an afternoon. Everything in this release was chosen
because it could be proven without one.
