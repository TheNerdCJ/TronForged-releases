## v0.420.0 - a ticket can know which machine it is about

**Nothing visible changes yet.** This release lays the groundwork the ticketing work needs,
closes two ways the next schema change would have broken upgrading from the old database,
and repairs two build-time safety checks that had quietly stopped being able to fail.

### A ticket can now name the machine it is about

Until now a ticket carried the machine as **typed text** - whatever somebody wrote in the
box. A ticket can now also carry the enrolled console it concerns: a real machine in your
fleet, the one a technician connects to.

That is deliberately **not** the same thing as the device registry a ticket could already
point at. The two answer different questions and both are kept:

- the **console** is a machine your shop manages, running an agent, in the fleet;
- the **registered device** is the customer's own property brought to the counter - a
  games console, a phone, a TV - things that will never run an agent.

A ticket may carry either, both or neither, and nothing in the product treats one as a
substitute for the other.

Messages on a ticket can also carry a **role** now: an ordinary message, a resolution, a
cause, or a work log. One rule is enforced wherever a message is saved rather than left to
each screen to remember: **a cause and a work log are always shop-internal.** Customer-facing
views filter on that internal flag alone, so a diagnosis saved as customer-visible would
otherwise have landed in the customer's own message thread and their notification. A
resolution stays customer-visible, because that is the one they are meant to read.

Nothing uses these yet - the screens that will come in later releases. They exist now so
that the work which needs them does not also have to change the database.

### Upgrading from the old database keeps working

The server moved from PostgreSQL to its own embedded database some releases ago, and shops
on the old one can still import. That import deliberately **refuses** rather than copying
a partial picture: if the old database is missing anything the new one expects, it stops,
because a copy that quietly leaves a table or column empty is worse than no copy.

That strictness had a trap in it. Anything added to the new database *after* the move
cannot possibly exist in an old one - so the next new table or column would have made the
importer refuse every remaining shop's data. Not gradually: outright, on the first change.

Both halves are now separated properly. What the new database contains and what an import
is entitled to expect are two different lists, and this release adds the first entries to
the "new since the move" side. Existing data is unaffected, and an import from an old
database now succeeds where it would have refused.

### Two safety checks that could never have failed

Both of these were checks the build runs on every release, and both were passing for the
wrong reason. Neither turned out to be hiding a real fault - but a check that cannot fail
is not protecting you, it is only telling you it is.

**The first** refuses a whole category of column: anything that would record whether you
opened an invoice. That refusal is deliberate and documented, and the check exists so a
later release cannot quietly undo it. It was reading the **old** database's list of
changes, not the one your server actually runs - so for several releases the refusal
applied to a database nobody uses any more. It now reads both.

**The second** is the one that proves no database query in the product is ever built by
gluing typed-in text into it - the mistake behind most break-ins of this kind anywhere.
The check was looking for a marker that no longer existed, so it matched nothing and
reported success every time. It now looks for the right one, and **with it working
properly, all ~188 of the product's database queries pass.** The queries were correct all
along; the proof was not.

### Worth knowing

**Nothing on your server needs doing.** The database update applies itself on the next
start, adds two empty columns, and changes no existing row.
