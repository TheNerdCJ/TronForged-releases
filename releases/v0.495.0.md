# v0.495.0 - TronForged 0.495.0 - a faster fleet, online and offline times, the Windows build, one tray icon, and safer updates

# TronForged v0.495.0

The fleet opens faster and says how long each machine has been online or away. Installed apps shows the version that
runs, an administrator's PC shows one tray icon, and updates are safer and easier to steer. The remote pointer stays
under yours in full screen, and the fleet names each PC's Windows version and build.

## The fleet opens faster

- **At once, then fresh.** The Unattended Fleet window and the Fleet and remote page share one copy of the machine
  list. Opening either one paints the last list straight away and says *Showing the list read at 14:02:10 -
  updating.* until the new list arrives.
- **Machines first.** The Unattended Fleet window shows the machines as soon as they arrive and adds the disk-image
  coverage when it comes.
- **Less work on your console.** Only the rows that changed are redrawn. The search waits a quarter of a second after
  you stop typing. A tile builds its menu and its long tooltip when you open them. After a reconnect the list is asked
  for at once instead of at the next 20-second tick.
- **Less work on your shop server.** It answers the fleet lists beside your console's other requests instead of behind
  them, reads each table once per list whatever the size of your fleet, sends only the customers and site details
  the list needs, and writes one log line with the counts and the time a list took (never a name) when a list is slow,
  and once a quarter-hour otherwise.
- **Nothing else changes.** The same rows, facts, filters, counts and actions, and the same rules for who sees what.
- Not yet measured on a large real fleet.

## Online for, offline for

- Each machine now says *Online for 3 h 20 min*, *Offline for 2 days*, *Not seen for 5 h* (enrolled but never
  reported) or *Never seen*: on its tile, in its Device details, in the last column of the Fleet and remote page (now
  *Online / last seen*) and in the row's detail.
- With a shop server older than 0.495.0, and for a machine that was already online when you updated the shop server,
  it says plain *Online* until that machine next comes online.

## Windows version and build

- A row's detail on the Fleet and remote page adds **Operating system**, for example *Windows 11 Pro 24H2 (build
  26100.4061)*, just above **Version**. A tile's tooltip shows the same text.
- A Windows 11 PC is no longer named Windows 10. A PC still on an older TronForged keeps sending its old short name
  until it updates.
- TronForged runs on Windows only: macOS and Linux are not supported.

## Installed apps and the tray icon

- **Installed apps shows the version that runs.** Every start of the installed console refreshes its entry in
  Windows' Installed apps, so after an update it shows the new version, not the one first installed. The old program
  was never left behind: an update replaces the one program in place.
- **One tray icon.** On an armed PC signed in with an administrator account you now see one TronForged icon, with your
  shop's icon. The small per-user tray steps aside while the console's own tray is up and comes back when the console
  closes. Uninstalling ends it, and an update restarts it on the new program.

## Updates on each PC

- The background service moves onto a console-applied update within minutes.
- The previous build is kept for at least three days and until the new one has reached your shop server. While it is
  kept, **About** offers **Go back to <version>**. It asks first, and TronForged restarts onto that build when nothing
  is running. The version you went back from is not installed again, unless a technician's *Update now* asks for it; a
  newer release is.
- A kept build older than 0.495.0 does not know that rule itself. After **Roll back this PC**, your shop server does
  not offer that PC the version it went back from again, until a newer release or an *Update now*; the shop server
  forgets this when it restarts, and that PC then updates again at its next check. After **Go back to** in About, to
  a build older than 0.495.0, that PC updates again at its next check unless your shop pauses or recalls the release.
- The title bar shows the version, and About says *<version> installed - restarts when idle* when a newer program is
  already on disk.
- A release your shop marks as required installs at the next idle minute, and *Not now* is offered once.
- **What changed**: the restart notice and About show the first lines of the release notes, and a customer's PC says
  once, from its tray, what the update brought.
- A scheduled download waits while the PC is on a metered connection. Press **Check for updates** to download it now.
- When your shop server offers it, a PC downloads only the pieces of the new program it does not already have. Not yet
  measured on a real update.
- The full-control helper is replaced at a console's start only when no remote session is live.
- Every step goes to one log per PC, `logs\update.log`, which the Support Bundle carries.

## Steering updates from the Server Console

- **Each PC's update state** on its tile and in its row's detail: downloaded and what it waits for, on trial, the
  build it keeps, and the last update's outcome. A PC behind a required release says *Missing the required update
  <version>.*
- **Adoption.** Each published release on the catalog says *on it: N of M PCs* (and how many rolled back).
- **Rollout waves.** **Roll out in waves** sends a build to 10% of your PCs, then 50% after 12 hours, then everyone
  after 12 more. It stops at the first failed update report from a PC on it and waits for you: **Continue waves**,
  **Roll out to all PCs now** or **Recall**. Nothing moves on by itself, and the waves wait while automatic updates
  are paused. **Roll out to all PCs now** is still there for one click.
- **A console older than 0.495.0 shows a wave below 100% as going to everyone.** That is only how it shows it: your
  shop server decides which PCs are offered the build.
- **Roll back this PC.** On a tile's menu, or a row's detail, a technician with the remote permission can send one PC
  back to the build it kept. It is never a download, only that PC changes, and it is recorded in the audit log.
  **Recall** now points at it for the PCs that already have a recalled build.
- **The shop server goes first.** A console release newer than your shop server waits until the server has updated
  itself to that version. The Status page says so, and **Publish to canaries** still sends it on at once.
- **Update hours and a bandwidth cap.** Choose when your shop server sends console updates and how fast all of them
  together may go. Outside the hours a PC tries again later. A technician's *Update now* is sent at any time.

## The shop server's own update

- It survives a power cut part-way through: the next run of its task, or the next restart, finishes the update or puts
  the previous program back.
- Its entry in Installed apps shows the version it runs.
- Before it updates, it keeps a verified copy of its database. When the new program has come up, that copy is removed
  (a copy that could not be finished is removed too: at once, or by the next run when the update was cut short while
  copying). If the new server program does not start and the previous
  one is put back, the copy is kept and the Status page offers it, saying how many changes were written since. **Only an
  administrator can restore it, on the server box itself**, by typing RESTORE; the database it replaces is kept beside
  it. **Keep the current database** closes the offer. Nothing is restored by itself, and a copy that was offered is
  never deleted by itself.
- If the new program cannot be renamed into place and the previous one cannot be put back either, the result says so:
  the server is not running until the server box restarts (which puts the previous program back), or until an
  administrator renames `TronForged.Server.exe.prev` back to `TronForged.Server.exe` and starts the service.
- Everything in this section starts with the update after 0.495.0: the update of your shop server to 0.495.0 itself
  is carried out by its installed 0.494.x updater, which works as before.

## Remote desktop

- The customer's pointer now stays under yours when the Remote Desktop window is maximised or full screen, and moves
  at once when you resize the window. Clicks always landed in the right place; only the drawn pointer drifted.
- For an I-beam or hand pointer on a customer PC at a scaled display setting, the drawn tip can still sit a few pixels
  off.

## Versions

- Update your shop server first. Online for, adoption, waves, the update hours, Roll back this PC and the database
  copy need the shop server on 0.495.0. A PC's update state and Roll back this PC need that PC on 0.495.0 too.
- With an older shop server the fleet works as before, with plain *Online* and the single **Roll out to all PCs**.
- **Go back to** in About on a PC that keeps a 0.494.x build: once it runs, that older build reports a failed update,
  on any shop server, and the release it went back from is held (the canary brake and the wave latch) until an
  administrator continues it. On a shop server older than 0.495.0 the same happens whatever build the PC keeps. For a
  deliberate rollback of a PC that keeps a 0.494.x build, use **Roll back this PC** on the fleet: a 0.495.0 shop server
  does not count that as a failure.
