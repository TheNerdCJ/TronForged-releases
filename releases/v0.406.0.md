## v0.406.0 - Boot in VM could never have worked on a modern disk, and now the tests run a real one

**Booting a captured image in a virtual machine failed every time on any UEFI/GPT image, with a
bare "error 1005". The cause was one wrong assumption, shared by the restore. It is fixed, and the
test that would have caught it now runs an actual disk instead of reading a script.**

### What was wrong

When TronForged prepares a disk it asks Windows to convert it to the modern GPT layout. **Windows
quietly adds a small reserved partition of its own during that step**, before TronForged creates
any of the partitions the image describes. So a disk that should hold four partitions comes back
holding five.

TronForged then matched each captured volume to a partition by counting positions. With an extra
partition in front that nobody counted, every match after the first was one out, and Windows was
told to write a 214 GB Windows volume into a 16 MB reserved partition that has no file system at
all. The tool doing the writing reported that as error 1005, "the volume does not contain a
recognized file system", after spending nine minutes on the integrity check first.

The same assumption was in the restore. It failed safely rather than destructively, because it
compares the partition count against the image first and refuses when they disagree, so nothing was
ever written to the wrong place. But it means **restoring to a GPT disk would have stopped dead**
with a message about the layout not applying as written.

### What changed

Partitions are now matched by **what they are** rather than where they sit. A partition that
nothing is ever written to cannot shift the mapping, whether Windows added one, two, or none. The
rule is written once and both the restore and the virtual-machine builder call that same one, which
matters: a second copy of this rule is what caused the fault.

The refusal in the restore stays, because it was right, and now reports what it actually found.

Two smaller repairs sit alongside. A virtual machine run that fails now removes the virtual disk it
created, so the next attempt reports the real problem instead of complaining about leftovers from
the last one. And the script it generates is kept when a run fails, with its location in the status
line, so there is something to look at afterwards.

### The test that would have caught it

None of this was caught because **the test suite had never once run the disk tool it generates
commands for**. Every check compared the generated text against an expected answer, and those
answers were written from the same assumption as the code, so they agreed with each other and with
nothing else.

There is now a test that creates a scratch virtual disk, runs TronForged's own commands against it,
and checks that the matching survives the partition Windows adds unasked. It needs administrator
rights, so on an ordinary run it does not execute - and when it does not, **it says so loudly and
names itself as the check that would have caught this**, rather than passing quietly. A test that
skips in silence reads as coverage, which is how this shipped in the first place.

### Worth knowing

This is proven against a scratch virtual disk and against the exact partition shape the fault
produced, not against real hardware. The first genuine virtual-machine boot and the first genuine
restore to a GPT disk are now named in the bench plan.
