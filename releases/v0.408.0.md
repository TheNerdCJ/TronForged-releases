# v0.408.0 - v0.408.0 - a new machine can enrol through a proxied address

## v0.408.0 - a new machine can join through a proxied address, and a failure says what it saw

**A brand-new PC could not enrol against a shop whose address sits behind Cloudflare's proxy, and
the message it showed blamed the address and the server. Both were fine. Enrolment now finds the
shop the way an enrolled machine already does, and every way it can fail now reads differently.**

### What was wrong

A shop can put its public name behind Cloudflare's proxy. That hides the shop's IP address and is a
supported, recommended setup - the web transport exists for it.

Cloudflare's proxy carries a fixed set of HTTPS ports, and it dials the shop on the **same port the
visitor named**. The enrolment port is not one of them.

An **already-enrolled** console was never affected. It holds a profile that names the shop's web
transport port, so it rides the proxy and connects. A **brand-new** machine holds nothing. It dials
whatever port is written in the address it was handed, which by default is the enrolment port - and
that dial never leaves Cloudflare. It waits, and times out.

So every machine in the shop kept working perfectly while no new one could join. That is what made
it hard to see, and it is why the shop's own Server Console showed green throughout: the check it
was running asked whether the **transport** port could cross the proxy. It could. Nothing asked
about the port a new machine would actually dial.

### What changed

**Enrolment now tries the web transport.** When the port it was given does not answer, it tries the
ports a proxy can carry, and it does that for both doors - the six-digit approval a customer uses and
the pairing code a technician uses. Both now run the same code. They had the same defect, and fixing
one would have left the other broken.

**Nothing counts as your shop server until the handshake proves it.** This matters more than it
sounds. Through a proxied name, every carried port answers and presents a valid certificate, whether
or not anything is behind it - you are talking to Cloudflare, not to the shop. On the network where
this was found, one of those ports reached the building's router. So a connection opening proves
nothing, and only the pinned handshake is allowed to end the search. A fix that trusted an answered
connection would have been worse than the fault.

**The failure now says what it saw, not what it guessed.** Four outcomes that used to read as one
sentence:

- the server answered on a **different port** than the one you gave, and it names the port that worked
- **nothing answered anywhere**, which is the only case the old message actually fitted
- the **name did not resolve** at all
- the port **could not cross** what sits in front of that name

It does not name a cause it cannot see. It reports what it observed and leaves the diagnosis alone.

The old advice about being inside the shop was the one correct part of the message, and it stays -
but it now appears only when nothing answered at all, so it no longer misdirects somebody whose real
problem is the port.

**The server tells you before a customer finds out.** If the address you hand out ends in a port a
proxy cannot carry, the Web transport page says so, and says which port to hand out instead. It stays
quiet when it has read your DNS record and knows it is not proxied, and it says "if" rather than
asserting when it has not read the record - it cannot see your dashboard from where it runs.

### For shops using a proxied address

Hand out your **web transport port**, not the enrolment port. The setup guide now says this in the
two places that tell you what to write down, and explains why.

This is a different failure from the one where a machine **inside** the shop cannot reach the shop's
own public name. That one fails from inside and works from outside; this one fails from outside and
works from inside. The guide now tells them apart, because the cure is not the same.

### Unreadable dropdowns, in eleven places

The "Who is this machine for?" picker on the approval card rendered as white text on a white box.

Windows draws its own chrome for that control and ignores the background an application sets, so a
light box with pale text is what you get unless the control's template is replaced. That replacement
existed already - in one window's private settings. The approval card is a different window, and in
Windows a new window inherits nothing from the one that opened it, so the fault came back somewhere
the original fix could not reach.

Fixing the reported one found **ten more dialogs** with the same defect, six of them equally
unreadable. All of them are fixed:

- choosing a USB disk, and choosing a backup to restore
- the Service Desk trio reception uses daily - which device a repair is about, registering or
  editing a device, and taking a payment or recording a refund
- managing a chat group
- two imaging dialogs, and two Windows-update dialogs in the Server Console

They were fixed at the **window factories** rather than at eleven call sites, so three of the
Service Desk dialogs were repaired by one change. There is now **one definition** of that chrome,
and a check that constructs the real windows from the shipped program and reads the colours back -
in **both** the light and dark theme, because a dialog pinned to one palette is the same bug one
theme change later.

### Worth knowing about the light theme

While proving the above, the check measured something separate and older: **the console's palette is
only half applied when you change theme.** Eleven of its seventeen colours are locked at startup and
ignore the switch; six do change.

The practical effect is that under the **light** theme some dialog headings sit pale-on-pale. The
pickers repaired above are **not** affected - they carry their own colours and read correctly in
both themes - and neither is the dark theme, which is what the console ships with.

This is not new and nothing in this release caused it: the file responsible is untouched here.
Repairing it means letting four palettes repaint for the first time, which is a visible change across
every screen and deserves its own release rather than being bundled into this one. Until then the
check **measures and prints it on every run**, so it cannot quietly drift.

### Worth knowing

**None of this has run on real hardware.** It is proven against fixtures that replay each step,
including a real handshake and a real web-transport upgrade, and against measurements taken from a
live proxied address. No customer machine has enrolled through the new path yet.

**One check is still owed** and it is named in the bench plan: a brand-new machine enrolling from
outside the shop, against the address the server itself publishes. Substituting a raw IP address does
not count - that is a different route, and it is the substitution that would hide the fault.

**The off-site check still reports only which route answered.** When a shop is proxied, the direct
port is supposed to be silent, so that is not a fault - but the check does not yet say which of the
two routes carried it. That is a separate surface and it has not been changed here.
