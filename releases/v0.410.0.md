# v0.410.0 - v0.410.0 - your shop's icon, the helper, and the light theme

## v0.410.0 - your shop's icon was never readable, the helper could half-install, and the light theme was half a theme

**Four repairs, all of the same kind: something reported success and had not actually worked. One of
them needs an action from you after updating - see the first section.**

### Your uploaded program icon could not be read at all

If your shop uploaded a program icon, it is almost certainly not being shown anywhere except the
system tray. Title bars and the taskbar have been showing the plain TronForged icon instead.

The icon builder squares the image up and writes each size into one file. For an image with no
transparency it dropped the transparency channel to save space, which is correct for your report
logo, while the index inside the icon file went on declaring every size as having one. Windows
rejects a file whose index disagrees with its contents, and it rejects it silently.

**A square, solid logo was the case that broke. A non-square one worked by accident**, because
squaring it up adds transparent bars and puts the channel back. So the most natural thing to upload
was the thing that failed.

**What you need to do, and the order matters.**

1. Update the **Server Console** first.
2. Then re-upload your icon from it.

The re-encode produces a readable file and your fleet picks it up by itself. **Do it in the other
order and it gets worse**: an older Server Console rebuilds the same broken file and stamps it as a
new version, so every machine takes the bad icon again and believes it is current.

**Machines do not heal on their own.** The corrected builder cannot repair a file already sitting on
a PC. Nothing changes out there until you re-upload.

The builder now refuses to assemble a file whose index would disagree with its contents, rather than
producing one and leaving Windows to reject it. And a console no longer holds the icon file open, so
the next brand change can actually replace it - without that, one good icon would have been the last
one a machine could accept.

### The full-control helper could half-install and never recover

The helper is what lets a technician reach the sign-in screen and elevation prompts. Installing it
is two steps: create the service, then start it. When the create succeeded and the start did not,
nothing ever tried again - both the first attempt and the fifteen-minute repair loop only looked for
a helper that was *missing*, and this one was present but stopped.

That machine armed, checked in, and showed as ready on the fleet, with no sign-in-screen control at
all. You would have found out one machine at a time, at the worst moment.

Repair now covers anything that is not actually running, and it can start a service that is merely
stopped. **It also runs before anyone logs in**, on the background service, which matters because
the machines that need it most are the ones nobody signs into. The runbook previously described
that self-repair; now it exists.

**The fleet can also see it.** A tile said "Ready for remote control", which was true of an attended
session and false at the sign-in screen. That is now two separate lines, and the sign-in-screen one
can say it does not know rather than guessing.

### The light theme was only half a theme

Changing theme repainted six colours out of seventeen. The other eleven refused and said nothing.

The result was worse than nothing happening: dialogs came out with a light background and the dark
theme's near-white text still on top, so headings that set no colour of their own were unreadable.

The cause was subtle and worth stating, because it is not where anyone looked. Sealing a style
freezes any brush held directly inside it, and a shared colour referenced from a style setter is the
same object as the one in the palette - so the act of sealing froze the palette. The correlation was
exact: the styles referenced eleven distinct colours, and those were the eleven that would not move.

Those references now go through a binding, which holds no brush to freeze, so all seventeen stay
changeable. **Light, midnight, slate and contrast now apply properly for the first time.** The dark
theme is unchanged.

And a recolour that cannot be applied is no longer silent. It records which colour, and why, and it
reads the value back afterwards to catch a change that appeared to work and did not.

### The console can tell you whether a PC is allowed to wake itself

The maintenance schedule has long had a "wake the PC" option. Ticking it only works if the power
plan permits wake timers, which is off on plenty of machines and off on battery on many laptops.

The check for that was written eleven months ago and **has never once been called**. It is now, and
the schedule says what is permitted rather than implying it will work. Mains and battery are
reported separately, and "only important wake timers" is shown as its own state rather than being
rounded to on or off.

The write is also checked now. Setting the wake flag discarded its own result, and the status was
read back with a command that cannot see that flag at all, so it could fail and still report the
schedule as applied.

**A wake timer cannot start a PC that is fully shut down.** It wakes one that is asleep or
hibernating. The wording says so rather than leaving you to find out.

### Worth knowing

None of this has run on real hardware. The helper repair before login, in particular, has never been
exercised on a machine nobody signs into, which is precisely the case it exists for.
